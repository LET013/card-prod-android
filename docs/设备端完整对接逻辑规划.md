# 设备端完整对接逻辑规划

更新时间：2026-07-21

## 1. 文档结论

现在不能再按“看到一个问题修一个问题”的方式推进。设备端必须按固定运行模型实现：

1. UI 层只负责展示和用户交互，不直接推导业务真相。
2. Android 数据层维护本机真实状态，包括卡槽状态、员工、人脸模板、同步版本、事件队列。
3. 通信层只负责收发：串口、MQTT、HTTP。通信收到结果后只能更新数据层，或者从数据层取快照上报。
4. 后台所有指令和 UI 所有按钮最终都进入 Android 的同一套业务入口，避免“页面按钮一套逻辑，后台下发一套逻辑”。
5. 错误必须统一进入诊断事件队列，本地保存，并在网络可用时通过 MQTT/HTTP 上报给后台。

文档主线以 `Android客户端接口文档.md` V4.1 为准；`智能工卡发卡机APP通信协议文档.md` 和 Excel 里的 V1.5 协议用于串口；旧 APP PDF 只作为配置项和操作习惯参考，不再以旧 TCP code=101/112 协议作为主线。

## 2. 目标架构

### 2.1 三层模型

| 层 | 职责 | 当前对应 |
|---|---|---|
| UI 层 | 首页、配置页、串口调试页、人脸页；只调用 JSBridge 和展示状态 | `uniapp/src` |
| 数据层 | 卡槽 Map、员工/人脸/指纹缓存、同步版本、本地事件日志、操作历史 | `SlotStateRepository`、`DeviceDataRepository`、`DeviceEventLogRepository` |
| 通信层 | HTTP 生命周期、MQTT 长连接、串口协议、虹软 SDK | `DeviceProvisioningManager`、`WebSocketConnectionManager`、`SerialConnectionManager`、`ArcFaceManager` |

### 2.2 统一业务入口

所有业务动作都应该进入 `DeviceCoreService`：

| 动作来源 | 入口 | 结果 |
|---|---|---|
| 后台远程开门 | MQTT `remoteOpen` | 串口开门、更新操作结果、上报响应 |
| 后台一键弹卡 | MQTT `remoteEjectAll` | 串口批量开门、上报批量结果 |
| UI 管理员开门 | JSBridge `cabinet.unlockDoor` | 同远程开门底层逻辑 |
| UI 一键弹卡 | JSBridge `cabinet.unlockAll` | 同远程一键弹卡底层逻辑 |
| 人脸识别成功 | JSBridge `face.verify` -> `ArcFaceManager` | 选择可取卡槽、串口开门、上报取卡 |
| 卡插入/取走 | 串口轮询返回状态变化 | 更新 SlotStateRepository、必要时上报 RETURN/TAKE 状态变化 |

## 3. 启动流程规划

启动应按以下顺序执行，不能跳步：

1. 读取本地配置：串口、波特率、槽位数量、服务器地址、设备凭证。
2. 获取稳定 `machineId`：优先本地配置，其次 Android ID。这个值不能随便变，否则后台会认为是另一台设备。
3. APP 版本检测：`POST /api/v1/app-version/check`。如果 `forceUpdate=true`，停止后续流程，展示升级状态。
4. 设备注册：`POST /api/v1/device/register`。拿到 `deviceToken` 和 `deviceCode`。
5. 设备激活：`POST /api/v1/device/activate`。后台已激活则拿到 `mqttPassword + signingKey + clientId`。
6. 注册码验证：如果 activate 只返回 `registerCode`，则用配置里的激活码调用 `POST /api/v1/device/verify`。
7. 获取配置：`GET /api/v1/device/config`。把后台配置合并到本地配置，例如波特率、槽位数量、轮询间隔、识别阈值。
8. 启动 MQTT：连接 broker，订阅 `card/{deviceCode}/down` 和 `card/{deviceCode}/down/response`。
9. MQTT 登录：上行 `login`，带根级 `deviceCode` 和 HMAC sign。
10. 心跳：每 30 秒发 `heartbeat` 到 `card/{deviceCode}/heartbeat`。
11. 启动数据同步：主动拉员工、人脸、指纹数据。
12. 启动串口：打开配置的串口，开始轮询。
13. 首次自检/状态上报：把 MQTT、HTTP、串口、人脸引擎、卡槽摘要上报。

当前代码基本有这些模块，但启动阶段还需要增强：每一步的失败都要进入统一诊断事件，UI 启动页应展示当前阶段，而不是笼统“加载失败”。

## 4. 后端通信规划

### 4.1 HTTP 和 MQTT 的边界

| 类型 | 使用 HTTP | 使用 MQTT |
|---|---|---|
| 注册/激活/验证/配置 | 必须 HTTP | 不使用 |
| 人员/人脸/指纹分页同步 | 推荐 HTTP | 可由 MQTT 指令触发 |
| 文件下载、图片下载、升级包 | 必须 HTTP | 不传大文件 |
| 登录、心跳、远程指令 | 可作为降级 | 主通道 |
| 卡事件、状态、故障、日志 | HTTP 可补发 | 主动实时上报 |

V4.1 的正确理解是：MQTT 管实时，HTTP 管生命周期、大数据和降级补偿。不要再把旧 TCP socket 当成主线。

### 4.2 MQTT 消息要求

所有设备上行必须统一封装：

```json
{
  "msgId": "msg_时间戳三位随机",
  "cmd": "statusReport",
  "timestamp": 1753001234567,
  "deviceCode": "01CD7DEE",
  "sign": "HMAC-SHA256 Base64",
  "data": {}
}
```

设备端需要补齐：

1. 上行所有消息必须复用同一个 envelope 构造逻辑。
2. 下行消息要做 `msgId` 去重，避免后台重试导致重复开门。
3. 下行消息虽然文档说不含 sign，但仍要校验 cmd、timestamp 合理性、deviceCode 兼容字段。
4. 每个远程操作要生成 `operationId`，贯穿串口发送、串口应答、业务上报、错误日志。

## 5. 数据同步规划

### 5.1 同步触发时机

必须有四种触发：

1. APP 启动且 MQTT 登录成功后主动同步一次。
2. 后台下发 `syncUser` 时全量/增量同步。
3. 后台下发 `syncEmployeeData`、`syncFaceData`、`syncFingerData` 时单项同步。
4. UI 调试页提供“手动同步”按钮，用于联调。

### 5.2 人脸同步策略

一期客户端接虹软 SDK，识别决策在客户端，因此客户端必须最终持有可比对的人脸模板。

推荐请求：

| 场景 | includeFlags |
|---|---|
| 联调/排查 | `7`，特征值+图片 URL+图片 Base64 |
| 正式运行 | `3`，特征值+图片 URL |
| 后端没有客户端可用特征值 | `2`，图片 URL，由客户端下载并提取特征 |

实现原则：

1. 优先导入 `faceFeature`，但必须校验 `featureVersion` 和当前虹软 SDK 是否兼容。
2. 如果特征值不可用，下载 `faceImage`，客户端用虹软提取特征并保存本地模板。
3. 不建议长期同步 `faceImageBase64`，100 人以上会明显变慢，只适合调试或内网小规模。
4. 每个人脸导入都要记录成功/失败原因，失败原因要能上报后台。
5. 删除/停用员工或人脸时，必须删除本地模板；当前这块需要补齐。

### 5.3 “未登记人脸”的判断链路

用户后台上传照片后，手机识别提示“未登记人脸”，只能是下面几类：

1. 同步根本没拿到该员工或人脸记录。
2. 拿到了 face 记录，但 `faceTemplateImport.successCount=0`。
3. 图片下载失败或图片没有检测到唯一人脸。
4. 虹软引擎未激活或 ABI/授权不匹配。
5. 本地模板有，但活体帧提取失败。
6. 比对分数低于阈值。

所以 UI 和日志里必须展示：员工数、人脸记录数、本地模板数、最后一次导入成功数、失败列表、识别最高分。

## 6. 串口逻辑规划

### 6.1 协议基准

串口协议按 V1.5：

| 功能 | 功能码 | 方向 |
|---|---|---|
| 查询状态 | `0x01` | APP -> 单板 |
| 开门控制 | `0x51` | APP -> 单板 |
| LED 亮度 | `0x52` | APP -> 单板 |
| 读取版本 | `0x53` | APP -> 单板 |
| 升级使能 | `0x80` | APP -> 单板 |
| 升级传输 | `0x81` | APP -> 单板 |

帧格式：

```text
DD CC + 长度2字节 + F0 + 从机地址 + 功能码 + 数据域 + CRC16高字节 + CRC16低字节
```

CRC 计算范围是从 `DD CC` 到 CRC 前，CRC 高字节在前。

### 6.2 串口执行模型

串口必须单线程队列化：

1. 任何时候只允许一个等待应答的命令。
2. 自动轮询和手动开门不能并发。
3. 执行手动命令前暂停轮询。
4. 命令发送后等待指定功能码和地址的应答。
5. 超时后记录 `SERIAL_TIMEOUT`，更新对应卡槽为通信异常。
6. 命令结束后恢复轮询。

当前 `SerialConnectionManager` 已经接近这个模型，但超时、地址映射和错误上报还要加强。

### 6.3 卡槽 Map 模型

Android 数据层必须维护：

```text
Map<slotId, SlotState>
```

字段至少包括：

| 字段 | 说明 |
|---|---|
| slotId | 真实卡槽编号，1-100 |
| boardAddress | 串口从机地址 |
| groupNumber | 分组编号 |
| groupSlotNumber | 组内编号 |
| status | EMPTY/OCCUPIED/CHARGING/FULL/FAULT/UNKNOWN |
| cardNo | 卡号 |
| workCode | 协议工作状态 |
| doorCode | 门状态 |
| cardCode | 卡状态 |
| faultMask | 协议故障位 |
| voltage/current | 电压/电流 |
| updatedAt | 最后更新时间 |
| stale | 是否超过 N 秒未刷新 |

UI 首页和后台状态上报都只能读这个 Map，不能自己猜。

### 6.4 当前最大风险：地址映射

V1.5 帧里只有“从机地址”，没有绝对 `slotId`。当前代码把 `slotNumber` 映射成：

```text
boardAddress = ((slotNumber - 1) % singleGroupCount) + 1
```

这个逻辑有风险：如果总槽位 100、单组数量 10，那么 1、11、21、31 都会映射到地址 1。除非硬件还有“当前组”的外部上下文，否则单靠返回帧无法知道这是哪个真实槽位。

后续必须和硬件/旧 APP 明确三件事：

1. 100 个卡位是否真的有 100 个不同从机地址。
2. `单组数量=10` 是 UI 分组、轮询批次，还是硬件地址重复。
3. 如果地址会重复，切组命令是什么；当前文档没有写切组命令。

在确认前，设备端不能把地址 1 的状态同时当成 1/11/21... 的状态。首页应保持未知，直到能确认真实 slotId。

### 6.5 轮询策略

推荐：

1. 默认单组轮询。
2. 若地址模式为 DIRECT，轮询 1..totalSlots。
3. 若地址模式为 GROUP_REPEAT，必须先实现组选择/组上下文，否则只能轮询 1..singleGroupCount。
4. 每次收到状态帧只更新对应 slot。
5. 超过 `staleTimeoutMs` 未更新的槽位标记 `UNKNOWN` 或 `COMMUNICATION_FAULT`，不要保留旧状态假装正常。

### 6.6 一键弹卡

协议没有“一条命令弹出所有卡”的功能码，所以所谓一键弹卡本质是 APP 顺序发送多条 `0x51` 开门命令。

正确逻辑：

1. 生成批量操作 `operationId`。
2. 暂停轮询。
3. 按地址/槽位顺序逐个发送开门命令。
4. 每条命令等待应答或超时。
5. 每条间隔 `commandGapMs`，不能把所有帧瞬间写入串口。
6. 汇总成功/失败列表。
7. MQTT 响应 `remoteEjectAllResp`。
8. 额外上报 `batchOperationResult`，包含每个槽位结果。
9. 恢复轮询。

如果硬件实际只有单组地址 1-10，则只能弹 1-10 对应的一组；要弹 100 个，必须先确认是否有 100 地址或切组机制。

## 7. 取卡、还卡、状态事件规划

### 7.1 取卡

正常用户取卡流程：

1. 用户点开始使用。
2. 客户端活体检测和人脸识别。
3. 匹配到员工后选择可取卡槽。
4. 串口开门。
5. 开门成功后上报 `cardEvent TAKE`。
6. 后续轮询发现卡被取走，更新卡槽状态为 EMPTY。

注意：开门成功不等于卡真的被取走。最终状态以串口轮询为准。

### 7.2 还卡

还卡不应只靠按钮生成事件。更可靠的逻辑是：

1. 柜门打开。
2. 用户插卡。
3. 串口轮询检测到 `EMPTY -> OCCUPIED/CHARGING/FULL` 或 cardNo 变化。
4. Android 根据状态变化生成 `cardEvent RETURN`。
5. 如果检测到非法卡，生成 `hardwareFault` 或业务告警。

当前如果 UI 点“还卡”就直接上报 RETURN，未来要改成“开门请求”和“插卡状态确认”分离。

## 8. 错误与诊断上报规划

### 8.1 目标

未来任何关键错误，后台都应该知道：

1. 设备启动卡在哪一步。
2. MQTT 是否连接、订阅、登录、心跳是否正常。
3. HTTP 哪个接口失败，状态码和 msg 是什么。
4. 串口发了什么、收了什么、哪个地址超时。
5. 人脸同步拿到多少、导入多少、失败原因。
6. 人脸识别最高分、阈值、失败原因。
7. 远程指令是否执行，失败在哪个阶段。

### 8.2 统一诊断事件结构

建议所有错误都写成：

```json
{
  "eventId": "EV-时间戳-随机",
  "level": "ERROR",
  "category": "SERIAL",
  "code": "SERIAL_TIMEOUT",
  "message": "单板10功能0x51在5000ms内未应答",
  "deviceCode": "01CD7DEE",
  "operationId": "OP-xxx",
  "msgId": "后台下发msgId",
  "slotId": 20,
  "stage": "OPEN_DOOR_WAIT_ACK",
  "durationMs": 5000,
  "context": {
    "serialTx": "DDCC...",
    "serialRx": "",
    "port": "/dev/ttyS5",
    "baudRate": 57600
  },
  "timestamp": 1753001234567
}
```

不要上报人脸图片、虹软特征值、身份证号等敏感数据。

### 8.3 上报通道

| 错误类型 | MQTT | HTTP |
|---|---|---|
| 普通日志 | `logReport`，受后台开关控制 | `/api/v1/log/report` |
| 硬件故障 | `hardwareFault`，必须主动发 | `/api/v1/fault/report` |
| 自检快照 | `selfCheckReport` | `/api/v1/device/selfcheck` |
| 批量日志补传 | 可选 | `/api/v1/logs/batch` |

当前 `DeviceEventLogRepository` 只本地保存，没有形成补传闭环。后续应增加 `DiagnosticReporter`：

1. `record(level, category, code, message, context)` 写本地队列。
2. 在线时立即尝试 MQTT/HTTP 上报。
3. 离线时保留队列。
4. 每 N 秒批量补传。
5. 后台 ACK 后删除已确认事件。
6. UI 调试页能查看最近 200 条诊断。

## 9. 当前代码状态判断

| 模块 | 当前状态 | 判断 |
|---|---|---|
| 注册/激活/配置 | 已有 `DeviceProvisioningManager` | 主线基本正确，需要更完整错误上报 |
| MQTT | 已有 Paho MQTT、签名、topic | 基本正确，需要下行去重、统一响应结构 |
| HTTP | 已有 `BackendHttpClient` | 可用，需要批量日志/下载/更细错误 |
| 串口协议 | 已有 V1.5 帧、CRC、查询、开门、版本 | 方向正确，最大风险是槽位地址映射 |
| 卡槽缓存 | 已有 `SlotStateRepository` | 方向正确，需要 stale/真实映射/状态变化事件 |
| 一键弹卡 | 已顺序发送开门 | 符合协议，但必须确认地址范围 |
| 数据同步 | 已拉员工/人脸/指纹 | 需要删除同步、失败补偿、UI 手动触发 |
| 人脸导入 | 已支持特征/图片 | 需要版本兼容判断、失败上报、模板数展示 |
| 错误日志 | 已有本地队列 | 不够，需要远程补传闭环 |
| UI 首页 | 可读 native slots | 需要严格显示 map 数据，不要 mock 覆盖真实状态 |

## 10. 后续实施优先级

### P0：先稳住联调主链路

1. 明确串口地址映射，决定 `slotId -> boardAddress` 是否 DIRECT。
2. 增加 `DiagnosticReporter`，所有 catch 都进入统一错误事件。
3. 串口每次 TX/RX/超时都带 `operationId`。
4. MQTT 下行 `msgId` 去重。
5. UI 调试页展示：deviceCode、MQTT 状态、同步统计、人脸模板数、最近错误、串口 TX/RX。

### P1：让首页状态可信

1. 首页只显示 `SlotStateRepository` 快照。
2. 未轮询到的槽位显示 UNKNOWN。
3. 超时槽位显示 COMMUNICATION_FAULT 或 STALE。
4. 串口状态变化触发 UI 更新。
5. 定时状态上报只上报已知槽位，并带 summary。

### P2：让人脸识别链路闭环

1. 启动成功后自动同步员工/人脸/指纹。
2. 手动同步按钮可强制全量同步。
3. 人脸导入失败明细可见、可上报。
4. 识别失败时返回最高分、阈值、模板数。
5. 支持员工/人脸删除同步。

### P3：完善业务事件

1. TAKE 上报和真实取走状态分离。
2. RETURN 由插卡状态变化触发。
3. 远程开门/管理员开门/人脸开门统一走同一操作记录。
4. 批量弹卡上报 `batchOperationResult`。

### P4：完善运维能力

1. APP 强制升级流程。
2. 固件升级真实下载、校验、串口升级。
3. 授权状态定期检查和变化上报。
4. 远程日志开关、批量日志补传、设备自检常态化。

## 11. 和后端/硬件必须确认的问题

1. 当前设备 `totalSlots=100` 时，串口从机地址到底是 1-100，还是 1-10 重复。
2. 如果是重复地址，是否存在切组命令；文档目前没看到。
3. `faceFeature` 是否由同版本虹软 SDK 提取，是否能被 Android 端直接 compare。
4. 后台下发 `syncUser` 后，是希望客户端主动 HTTP 拉取，还是 MQTT 响应里返回数据。
5. `logReport` 是否必须受 enableLogUpload 控制；硬件/识别错误是否允许无开关强制上报。
6. `cardEvent TAKE` 是开门成功即算，还是检测到卡被取走才算。
7. 还卡是否要求用户认证，还是只按串口插卡状态自动上报。

## 12. 最终推荐实现路线

短期联调阶段，先把主链路固定为：

```text
启动 -> 注册/激活/配置 -> MQTT连接登录 -> 主动同步人员/人脸/指纹 -> 串口轮询更新Map -> 首页读Map -> 后台远程指令进入DeviceCoreService -> 串口执行 -> 结果/错误统一上报
```

不要再让 Vue 层自己承担通信判断，也不要把旧 TCP 协议继续混入主线。旧 APP 只保留三个经验：默认 57600、单组数量/单组轮询、管理员操作不受服务器限制。

真正上线前，必须先解决串口槽位映射和诊断上报闭环。否则首页颜色、人脸是否同步成功、后台能否看到错误，都会继续靠人工猜。
