## 三、当前层级问题诊断

### 3.1 严重：management 与 engineering 功能完全重叠

| 功能 | management.vue | engineering.vue |
|------|:---:|:---:|
| 单板升级 | ✅ | ✅ |
| APP 升级 | ✅ | ✅ |
| 一键弹出 | ✅ | ✅ |
| 硬件版本号 | ✅ | ✅ |
| 工作卡升级 | ✅ | ✅ |
| 指令验证（→ serial-demo） | ✅ | ✅ |
| 主板升级 | ✅ | ✅ |
| 权限过滤 | ✅ | ❌（无过滤） |

**两个文件实现了完全相同的功能**，仅权限处理不同。engineering 从 system 进入，management 从 admin 进入，但用户看到的是两套一样的菜单。

### 3.2 中等：category 分组不合理

**admin 仪表盘**的 5 个卡片混合了不同层级的内容：

| 卡片 | 性质 | 问题 |
|------|------|------|
| 角色管理 | 账号/权限管理 | 需要二级密码，安全敏感 |
| 用户管理 | 账号/权限管理 | 需要二级密码，安全敏感 |
| 系统设置 | 二级菜单聚合 | 本身只是入口，不执行功能 |
| 管理功能 | 设备维护/升级 | 功能集合 |
| 查看卡状态 | 实时状态查看 | 只读查询，非管理操作 |

→ 角色/用户（账号管理）和升级/弹卡（设备维护）混在同一个平面，缺少清晰的分类边界。

### 3.3 中等：system 与 feature 的职责混乱

- `system.vue` 是一个**纯菜单聚合页**，展示 10 个入口
- `feature.vue` 通过 `?type=` 参数兜底处理了 5 种完全不同的功能（修改密码、重启、授权、单元管理、历史管理）
- 其中 `?type=password` 和独立的 `change-password.vue` 功能重叠

### 3.4 轻微：路径深度不统一

- 人脸/指纹在 `biometric/`（合理）
- 人员管理在 `employees/`（合理）
- 但卡状态、配置、工程模式、管理功能都在页面根下（`pages/xxx/`），与 `pages/admin/`、`pages/system/` 同级，目录语义模糊

## 四、当前管理功能按性质分类

按功能性质重新归类：

### A. 账号与权限（安全敏感，需要密码/二级密码）
- 修改登录密码 (`change-password` / `feature?type=password`)
- 角色管理 (`role-manage`) — 二级密码
- 用户管理 (`credential-manage`) — 二级密码

### B. 设备维护与升级（需要谨慎操作）
- 单板升级
- APP 升级
- 工作卡升级
- 主板升级
- 一键弹出
- 硬件版本号

### C. 串口调试（深度诊断）
- 指令验证 → `serial-demo`（串口调试台）

### D. 系统配置
- 设备参数 (`config`)：串口、MQTT、识别参数、摄像头
- 系统授权 (`feature?type=authorization`)
- 重启应用 (`feature?type=restart`)

### E. 生物识别录入
- 人脸注册 (`biometric/face`)
- 指纹注册 (`biometric/fingerprint`)

### F. 数据管理
- 人员管理 (`employees`)
- 单元管理 (`feature?type=units`)
- 历史管理 (`feature?type=history`)

### G. 实时状态
- 查看卡状态 (`card-status`)

## 五、调整方案（已决策）

### 决策总览

| # | 决策 | 状态 |
|---|------|:---:|
| A | management + engineering **合并为「工程模式」**（保留 engineering） | ✅ 已定 |
| B | admin 仪表盘**按功能性质分区**（账号权限 / 系统设置 / 设备维护 / 实时状态） | ✅ 已定 |
| C | **移除 `feature?type=password`**，统一到 `change-password.vue`，并**升级 change-password 视觉**对齐 feature 的 modern 风格 | ✅ 已定 |
| D | system.vue **二级分组**（生物识别 / 数据管理 / 系统工具） | ✅ 已定 |
| E | 目录整理：删除 `pages/management/`，其余保持 | 跟随以上调整 |

### A. 合并 management + engineering → 「工程模式」

**变化**：

| 旧 | 新 |
|----|----|
| `management.vue`（7 项，有权限过滤，自定义 ModalShell） | **删除** |
| `engineering.vue`（7 项，无权限过滤，简化弹窗） | **保留并增强** |
| admin 中「管理功能」卡片 | **替换为「工程模式」**，指向 engineering |
| system 中「工程模式」卡片 | **移除**（避免重复入口） |

**调整后的 `engineering.vue`（新工程模式）**：
- 继承 management 的权限过滤逻辑（`hasPermission`）
- 继承 management 的 ModalShell 升级/弹卡/版本对话框
- 保留全部 7 项菜单：单板升级、APP升级、一键弹出、硬件版本号、工作卡升级、指令验证（→ serial-demo）、主板升级
- 卡片样式统一使用 `variant="line"`（与 management 一致）

**调整原因**：两个文件 7 项功能完全相同（见三、3.1），仅权限处理不同。管理功能/工程模式作为概念对用户无区分意义，合并消除维护负担和认知困惑。

### B. admin 仪表盘按功能性质分区

**当前 admin（旧）**：5 张卡片平铺，无分区，3 列网格

```
[角色管理] [用户管理] [系统设置]
[管理功能] [查看卡状态]
```

**新 admin**：分区卡片，有节标题

```
┌─ 账号与权限 ────────────────────────────┐
│  [修改密码]    [角色管理 🔒]  [用户管理 🔒] │
└──────────────────────────────────────────┘

┌─ 系统设置 ──────────────────────────────┐
│  [系统设置]                               │
└──────────────────────────────────────────┘

┌─ 设备维护 ──────────────────────────────┐
│  [工程模式]                               │
└──────────────────────────────────────────┘

┌─ 实时状态 ──────────────────────────────┐
│  [查看卡状态]                             │
└──────────────────────────────────────────┘
```

| 分区 | 卡片 | 目标页面 | 说明 |
|------|------|---------|------|
| 账号与权限 | 修改密码 | `change-password` | 无二级密码，视觉升级后（见 C） |
| 账号与权限 | 角色管理 🔒 | `role-manage` | 二级密码，`admin.manage` 权限 |
| 账号与权限 | 用户管理 🔒 | `credential-manage` | 二级密码，`admin.manage` 权限 |
| 系统设置 | 系统设置 | `system`（重组后见 D） | `system.menu` 权限 |
| 设备维护 | 工程模式 | `engineering`（合并后见 A） | `debug.command` / `upgrade.*` 权限 |
| 实时状态 | 查看卡状态 | `card-status` | `cabinet.view` 权限 |

**调整原因**：
- 旧方案中「角色管理/用户管理（需二级密码）」与「系统设置（聚合页入口）」与「管理功能（设备维护）」平铺在同一平面，缺乏分类边界
- 分区后用节标题明确功能域，用户一眼可分辨安全敏感操作（账号权限区）和日常操作（实时状态区）
- 新增「修改密码」常驻在账号与权限区，不再需要进 system → feature?type=password 才能改密码

### C. 移除 `feature?type=password`，升级 change-password 视觉

**旧方案两套密码修改的问题**：

| 维度 | `feature?type=password` | `change-password.vue` |
|------|--------------------------|------------------------|
| 入口 | system → 修改密码 | 首次登录强制修改 / admin 直接进入 |
| 角色选择器 | ✅ 可切换修改对象 | ❌ 只能改自己 |
| 图标 | ✅ 大圆形 lock 图标 | ❌ 无 |
| 卡片内标题 | ✅ "修改密码" 大号标题 | ❌ 仅在 toolbar |
| 输入框 | 无边框 + 浅灰背景, h=50-66px, r=12px | 有边框, h=44px, r=6px |
| 按钮 | 全局 gradient, 全宽, h=50-66px | 自定义较小按钮, 右对齐 |
| 间距 | clamp() 响应式, 宽大 | 固定 px, 紧凑 |
| 卡片 | 无边框无阴影, r=23px, p=30-56px | 有边框有阴影, r=12px, p=28px |

**变化**：

| 旧 | 新 |
|----|----|
| `feature?type=password` 作为独立类型存在 | **移除该 type 分支** |
| `system.vue` 中「修改密码」卡片 | **移除**（改密码入口提升到 admin 仪表盘） |
| `change-password.vue` 旧式表单样式 | **全面视觉升级** |

**`change-password.vue` 升级要点**：

1. **卡片内顶部增加图标 + 标题**：
   - 大圆形 lock 图标（黄色背景 `#ffc95b`，同 feature?type=password）
   - "修改密码" 大号标题（`clamp(20px, 2.7vw, 26px)`, `font-weight: 500`）

2. **输入框样式重写**：
   - 去掉 `border: 1px solid #cfd9e7`
   - 改用 `background: #f4f7fb; border-radius: 12px;`
   - 高度从 44px → `clamp(50px, 6.4vh, 66px)`
   - 保持 3 个输入框（原密码 + 新密码 + 确认）

3. **按钮替换**：
   - 移除自定义 `.primary-btn`
   - 使用全局 `primary-gradient-button`（全宽, clamp 高度, 居中）

4. **卡片升级**：
   - 去掉 `border` 和 `box-shadow`（或极轻微阴影）
   - `border-radius` → `clamp(15px, 2vw, 23px)`
   - `padding` → `clamp(30px, 4.5vh, 56px)`（从固定 28px）

5. **可选：角色选择器**：
   - 若业务需要，可加入 picker 来切换修改哪个角色的密码
   - 默认修改当前登录用户自己的密码

**调整原因**：
- 消除 `feature?type=password` 与 `change-password` 的功能重叠，减少维护
- `change-password.vue` 的 UI 远不如 `feature?type=password` 精美（有边框输入框、小按钮、无图标无标题），升级到 modern 风格统一视觉语言
- 把改密码从 system（需要点两次）提升到 admin 仪表盘（一次点击直达），减少操作层级

## 八、第二轮调整：管理界面 → 选项卡式全功能内联（2026-07-28 晚）

### 问题

用户反馈第一版 admin（4 分区卡片，点击进入子页面）的布局"很奇怪，不美观"：
- 输入密码进入 admin 后看到的仍是卡片集合，需要再次点击才到达功能
- admin 本身就是一个「二级导航」，而不是功能页面

### 决策：改为选项卡式全局仪表盘

**核心理念**：`/pages/admin/admin` 是一个单页仪表盘，切换 Tab 即可看到全部内容，不需要 `navigateTo` 进入任何 admin 级子页面。

### 新 admin.vue 结构

```
┌─────────────────────────────────────────────┐
│ AdminHeader [角色: XXX | admin]  [退出管理]   │
├─────────────────────────────────────────────┤
│ █ 账号权限 │  系统设置 │  设备维护 │  实时状态 │  ← Tab 栏
├─────────────────────────────────────────────┤
│                                             │
│  scroll-view（当前选中 Tab 的内容全部内联）     │
│                                             │
└─────────────────────────────────────────────┘
```

### 四个 Tab 的内容

| Tab | 内容 | 原先对应页面 | 处理方式 |
|-----|------|------------|---------|
| **账号权限** | 修改密码表单 + 角色管理（双栏 CRUD）+ 用户管理（双栏 CRUD + 二级密码修改） | `change-password.vue` + `role-manage.vue` + `credential-manage.vue` | **全部内联**，不需要 navigateTo |
| **系统设置** | 3 个二级分组（生物识别/数据管理/系统工具）的 AdminMenuCard 网格 | `system.vue` 的内容 | **内联卡片**，点击卡片 navigateTo 到深层功能页面（这些是独立功能页面） |
| **设备维护** | 工程模式 7 项菜单 + 升级弹窗 + 确认弹窗 + 硬件信息弹窗 | `engineering.vue` 的内容 | **全部内联**，弹窗也在 admin.vue 内处理 |
| **实时状态** | 卡位 10×6 网格 + StatusLegend + SlotDetailModal | `card-status.vue` 的内容 | **全部内联** |

### 关键设计点

1. **二级密码保护**：角色管理和用户管理区域在首次激活时需要输入管理二级密码（用 PasswordModal 弹窗验证），验证通过后该区域内联内容才会显示。

2. **升级流程**：使用 `services.getUpgradeFiles()` 获取升级文件列表，用户在弹窗中选择文件后调用 `services.startUpgrade(fileId, progressCallback)` 执行升级。

3. **一键弹出**：调用 `services.unlockAllDoors()`，弹窗确认后执行。

4. **硬件版本号**：调用 `services.getRuntime()` 获取运行时信息并展示。

5. **卡位开门**：调用 `services.unlockDoor(slotNumber)`。

6. **退出管理**：调用 `services.logout()` → `uni.reLaunch` 回到首页。

### 设备维护 Tab 实现细节（已完成，2026-07-28）

#### engMenuItems（7 项菜单）

全部 7 项直接内联在 admin.vue，无需跳转 engineering.vue：

| key | label | icon | 点击行为 | 分发逻辑 |
|-----|-------|------|---------|---------|
| `unlockAll` | 一键弹出 | `eject` | 打开确认弹窗 | `handleEngAction` 特殊判断 |
| `board` | 单板升级 | `board-upgrade` | 打开升级弹窗 | 4 个升级 key → 升级弹窗 |
| `app` | APP 升级 | `app-upgrade` | 打开升级弹窗 | 同上 |
| `workCard` | 工作卡升级 | `work-card-upgrade` | 打开升级弹窗 | 同上 |
| `mainBoard` | 主板升级 | `main-board` | 打开升级弹窗 | 同上 |
| `hardware` | 硬件版本号 | `hardware` | 打开硬件信息弹窗 | `handleEngAction` 特殊判断 |
| `command` | 指令验证 | `command-check` | navigateTo → serial-demo | `item.route` 判断 |

图标全部对齐 engineering.vue 的 `allMenus`（`board-upgrade` / `app-upgrade` / `eject` / `hardware` / `work-card-upgrade` / `command-check` / `main-board`），不再使用旧的 `refresh` / `upload` / `unlock` / `info` / `terminal`。

#### handleEngAction 分发逻辑

```js
function handleEngAction(item) {
  if (item.key === 'unlockAll') { confirmUnlockVisible.value = true; return }   // 确认弹窗
  if (['board', 'app', 'workCard', 'mainBoard'].includes(item.key)) {            // 升级弹窗
    activeAction.value = item
    selectedFile.value = upgradeFiles.value[0]?.id || ''
    upgradingProgress.value = 0
    upgradeVisible.value = true
    return
  }
  if (item.key === 'hardware') {                                                  // 硬件信息弹窗
    engInfo.title = '硬件版本号'
    engInfo.content = '硬件版本需由 Android 串口版本读取返回；当前页面不生成默认版本。'
    engInfo.icon = 'hardware'
    infoVisible.value = true
    return
  }
  if (item.route) { uni.navigateTo({ url: item.route }) }                         // 指令验证 → serial-demo
}
```

不再有 `switch` 和 `default` 分支（旧版统一跳转 `/pages/engineering/engineering`）。

#### 新增弹窗模板

**升级弹窗**（`upgradeVisible`）：IconGlyph 圆形图标 + 标题（`{activeAction.label}文件列表`） + 文件列表（单选 Radio） + 进度条（`upgradingProgress`） + 「马上升级」按钮。

**硬件信息弹窗**（`infoVisible`）：IconGlyph 圆形图标 + 标题（`engInfo.title`） + 内容文本（`engInfo.content`） + 「确定」按钮。

#### 新增状态

| 变量 | 类型 | 用途 |
|------|------|------|
| `upgradeVisible` | `ref(false)` | 升级弹窗显隐 |
| `infoVisible` | `ref(false)` | 硬件信息弹窗显隐 |
| `activeAction` | `ref(null)` | 当前升级项目引用（label/icon） |
| `upgradeFiles` | `ref([])` | 升级文件列表（`onMounted` 从 `services.getUpgradeFiles()` 加载） |
| `selectedFile` | `ref('')` | 用户选中的文件 ID |
| `upgradingProgress` | `ref(0)` | 升级进度百分比 |
| `upgrading` | `ref(false)` | 升级进行中标志（按钮 disabled） |
| `engInfo` | `reactive({title,content,icon})` | 硬件信息展示数据 |

`onMounted` 中调用 `services.getUpgradeFiles()` 预加载升级文件列表，失败时降级为空数组。
