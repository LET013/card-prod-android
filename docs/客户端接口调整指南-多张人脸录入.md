# 客户端接口调整指南 — 员工多张人脸录入

> 版本：v1.2 | 日期：2026-08-02 | 适用模块：终端APP（Android）

---

## 一、变更概述

### 1.1 核心变更

| 维度 | 变更前 | 变更后 |
|------|--------|--------|
| 人脸与员工关系 | 1:1（一个员工仅一张人脸） | **1:N**（一个员工可录入多张人脸） |
| 主/扩展图区分 | 无 | **无区分**，所有图片平等对待 |
| FaceAI 注册ID | `${employeeId}` | `${employeeId}_${faceId}` |
| 文件哈希去重 | 无 | **全局去重**（同一图片不能重复录入） |
| 每人上限 | 无 | **可配置**（默认3张，`system.face.maxPerEmployee`） |
| 删除方式 | 直接物理删除 | **软删除**（status → '9'），终端通过增量同步感知 |

### 1.2 影响范围

- **FaceAI 引擎**：注册 ID 格式变为 `${employeeId}_${faceId}`，识别返回后需按 `_` 分割取 `employeeId`
- **终端人脸底库**：需支持同一 `employeeId` 下存储多条特征记录
- **人脸同步协议**：新增 `faceAiId` 和 `syncAction` 字段区分增/删操作

---

## 二、FaceAI 注册 ID 规则

每条人脸特征在 FaceAI 中注册时，使用的唯一标识为：

```
faceAiId = ${employeeId}_${faceId}
```

其中：
- `employeeId`：员工 ID（Long 类型）
- `faceId`：人脸记录 ID（Long 类型，由服务端在新增时自动分配）

**终端解析示例**：
```
"10001_52"  →  employeeId = 10001, faceId = 52
```

## 三、HTTP 接口（控制面）

### 3.1 人脸图片上传

用于将本地采集的人脸图片上传到服务端，获取带域名的访问URL和文件哈希。

> **终端注意**：人脸图片上传和特征录入是**两步操作**。先调用此接口上传图片文件，拿到返回的 `fileName`（存储路径）和 `fileHash` 后，再调用 3.2 或 3.3 的录入接口。

**管理后台接口**（Admin）：

```
POST /system/employee/uploadFaceImage
Content-Type: multipart/form-data
```

| 参数 | 类型 | 说明 |
|------|------|------|
| `file` | MultipartFile | 人脸图片文件（支持 jpg/png/bmp 等常用图片格式） |
| `employeeId` | Long | 员工ID |

**响应**（`FaceImageUploadResponse`）：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {
    "url": "http://192.168.1.100:8080/profile/face/2025/08/02/10001_1722585600000.jpg",
    "fileName": "/profile/face/2025/08/02/10001_1722585600000.jpg",
    "originalFilename": "face_photo.jpg",
    "fileHash": "a1b2c3d4e5f6..."
  }
}
```

| 字段 | 说明 |
|------|------|
| `url` | 完整访问URL（可直接预览） |
| `fileName` | 服务端存储路径（后续录入时传此值） |
| `fileHash` | SHA-256 哈希（16进制字符串，录入时用于去重校验） |

**终端建议**：终端侧采集图片后，先在本地计算 SHA-256 哈希，上传后与服务端返回的 `fileHash` 对比，确保传输完整性。

### 3.2 录入人脸（管理后台）

管理后台人员在 Web 端为指定员工录入人脸特征。

```
POST /system/employee/uploadFace
Content-Type: application/json
```

**请求体**（`UploadFaceRequest`）：

```json
{
  "employeeId": 10001,
  "faceImagePath": "/profile/face/2025/08/02/10001_1722585600000.jpg",
  "faceFeature": "AQAAAA...", 
  "fileHash": "a1b2c3d4e5f6..."
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `employeeId` | Long | **是** | 员工ID |
| `faceImagePath` | String | **是** | 3.1 接口返回的 `fileName` |
| `faceFeature` | String | 否 | 人脸特征值（终端采集+FaceAI提取后传入） |
| `fileHash` | String | 否 | SHA-256 哈希，用于全局图片去重校验 |

**错误响应示例**：

```json
{
  "code": 500,
  "msg": "该人脸图片已存在（hash=a1b2...），同一张图片不能重复录入"
}
```

```json
{
  "code": 500,
  "msg": "员工[10001]人脸图片已达上限（3张），无法继续添加"
}
```

> **终端注意**：人脸图片上传和特征录入是**两步操作**。先调用此接口上传图片文件，拿到返回的 `fileName`（存储路径）和 `fileHash` 后，再调用 3.4 的录入接口。

| 字段 | 说明 |

**终端建议**：终端侧采集图片后，先在本地计算 SHA-256 哈希，上传后与服务端返回的 `fileHash` 对比，确保传输完整性。

### 3.4 录入人脸（终端APP → Gateway）

终端APP采集人脸后直接通过 HTTP 上报。

```
POST /api/v1/employee/face
Content-Type: application/json
```

**请求体**（`EmployeeFaceUploadRequest`）：

```json
{
  "employeeId": 10001,
  "faceFeature": "AQAAAA...",
  "faceImagePath": "/profile/face/2025/08/02/10001_1722585600000.jpg",
  "fileHash": "a1b2c3d4e5f6..."
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `employeeId` | Long | **是** | 员工ID |
| `faceFeature` | String | **是** | 人脸特征值（FaceAI 提取） |
| `faceImagePath` | String | 否 | 人脸图片存储路径（3.3 接口返回的 `fileName`） |
| `fileHash` | String | 否 | SHA-256 哈希，用于去重校验 |

> **注意**：人脸图片上传和特征录入在终端侧是**两步操作**。终端需先调用 3.3 的人脸图片上传接口（`POST /api/v1/employee/face/image`）上传图片，拿到返回的 `fileName` 后作为 `faceImagePath` 传入。如果终端不需要服务端存储图片文件，可不传 `faceImagePath` 和 `fileHash`。

### 3.6 删除人脸

```
DELETE /system/employee/face/{faceId}
```

执行**软删除**（status 置为 '9'），终端通过增量同步感知删除事件。删除后员工 `faceRegistered` 状态仍保持为 "1"（只要还有至少一条活跃人脸记录）。

**注意**：`faceRegistered` 变更为 "0" 需要手动或定时任务检测（当该员工不再有任何活跃人脸时）。

---

### 3.7 查询已注册人脸的员工ID列表（终端专用）

终端用于判断本地底库是否缺少某些员工的人脸数据。

```
GET /api/v1/employee/face/registered
```

**响应**：

```json
{
  "code": 200,
  "data": [10001, 10002, 10003]
}
```

返回所有存在活跃人脸记录（status='0'）的员工ID数组。终端可对比本地底库，发起差异同步。

## 四、MQTT 同步协议

### 4.1 请求

- **Topic（上行）**：`card/{deviceId}/up`
- **cmd**：`syncFaceData`
- **消息最大条数**：10条/页（默认），最大 30 条/页（人脸特征数据量较大）

**请求体**（`SyncFaceRequestData`）：

```json
{
  "cmd": "syncFaceData",
  "data": {
    "lastSyncTime": 1722585600000,
    "page": 0,
    "pageSize": 10,
    "includeFlags": 4
  }
}
```

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `lastSyncTime` | long | **是** | — | 上次同步时间戳（毫秒）。传 **0** 表示**全量同步**，传 >0 表示**增量同步**（返回该时间之后变更的记录） |
| `page` | int | 是 | — | 分页页码，**从 0 开始**（0, 1, 2, ...） |
| `pageSize` | int | 否 | 10 | 每页条数，最大 30 |
| `includeFlags` | int | 否 | 4 | 内容标志位（位掩码），见下表 |

**includeFlags 位掩码说明**：

| 位 | 值 | 含义 | 终端使用场景 |
|----|-----|------|-------------|
| bit0 | 1 (0x01) | 包含人脸特征值 `faceFeature` | 需要更新本地底库时启用 |
| bit1 | 2 (0x02) | 包含图片下载地址（`faceImage` 字段拼接完整URL） | 需要展示人脸图片时启用 |
| bit2 | 4 (0x04) | 包含图片 Base64 编码 `faceImageBase64` | 需要直接获取图片内容时启用 |

可组合使用，如 `includeFlags=7` 表示三者全要。**默认值为 4**（仅 Base64，兼容旧版客户端），如需特征值同步建议设置为 5（特征值 + Base64）。

### 4.2 响应

- **Topic（下行）**：`card/{deviceId}/down`
- **cmd**：`syncFaceDataResp`

**响应体**（`SyncFaceDataResponse`）：

```json
{
  "cmd": "syncFaceDataResp",
  "msgId": "msg_001",
  "data": {
    "code": 0,
    "msg": "success",
    "syncVersion": 1722585650000,
    "total": 25,
    "page": 0,
    "pageSize": 10,
    "hasMore": true,
    "faceFeatures": [
      {
        "faceId": 52,
        "employeeId": 10001,
        "faceFeature": "AQAAAA...",
        "faceImage": "/profile/face/2025/08/02/10001.jpg",
        "featureVersion": "1.0",
        "status": "0",
        "faceAiId": "10001_52",
        "syncAction": "ADD",
        "faceImageBase64": "/9j/4AAQ..."
      },
      {
        "faceId": 88,
        "employeeId": 10002,
        "faceFeature": "BgAAAA...",
        "faceImage": null,
        "featureVersion": "1.0",
        "status": "9",
        "faceAiId": "10002_88",
        "syncAction": "DELETE",
        "faceImageBase64": null
      }
    ]
  }
}
```

**响应顶层字段**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `code` | int | 0=成功，非0=失败 |
| `msg` | String | 结果消息 |
| `syncVersion` | long | 服务端同步版本时间戳（毫秒）。**终端必须存储此值**，下一次同步时作为 `lastSyncTime` 传入以实现增量同步 |
| `total` | int | 变更总条数 |
| `page` | int | 当前页码（从0开始） |
| `pageSize` | int | 实际每页条数 |
| `hasMore` | boolean | 是否还有更多分页数据。**为 true 时终端应 page+1 继续拉取** |
| `faceFeatures` | Array | 人脸特征数据列表 |

**faceFeatures 每条数据**（`FaceFeatureSyncItem`）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `faceId` | Long | 人脸记录ID |
| `employeeId` | Long | 员工ID |
| `faceFeature` | String | 人脸特征值（`includeFlags` 含 bit0 时有值，否则为 null） |
| `faceImage` | String | 图片存储路径（`includeFlags` 含 bit1 时与完整URL拼接，否则为 null） |
| `featureVersion` | String | 特征版本号 |
| `status` | String | 记录状态：`"0"` = 正常，`"9"` = 已删除 |
| `faceAiId` | String | FaceAI 注册ID：`${employeeId}_${faceId}` |
| `syncAction` | String | 操作类型：`"ADD"` = 新增/更新，`"DELETE"` = 删除 |
| `faceImageBase64` | String | 图片 Base64 编码（`includeFlags` 含 bit2 时有值） |

### 4.3 部门树权限范围（同步数据过滤）

**终端发起 `syncFaceData` 时，服务端只返回该设备有权限看到的人脸数据。** 权限判定基于部门树结构：

#### 数据关系

| 表 | 字段 | 含义 |
|----|------|------|
| `biz_employee` | `dept_id` | 员工所属部门 |
| `biz_device` | `dept_id` | 设备所属组织 |
| `sys_dept` | `ancestors` | 部门祖级列表（如 `"0,100,200"`） |

#### 过滤 SQL 逻辑

```sql
-- 设备同步时，只返回"员工 dept_id 属于设备 dept_id 及其所有子部门"的人脸
and employee_id in (
    select e.employee_id from biz_employee e
    where e.dept_id in (
        select dept_id from sys_dept
        where dept_id = #{deptId}           -- 设备自身部门
           or find_in_set(#{deptId}, ancestors) -- 祖先包含设备 deptId 的子部门
    )
)
```

`find_in_set` 利用 `sys_dept.ancestors` 字段实现树形递归——子部门的 `ancestors` 中包含父部门的 `dept_id`。

#### 具体示例

假设组织架构：
```
总公司(deptId=100, ancestors="0,100")
  ├── 研发部(deptId=200, ancestors="0,100,200")
  │     ├── 前端组(deptId=201, ancestors="0,100,200,201")
  │     └── 后端组(deptId=202, ancestors="0,100,200,202")
  └── 市场部(deptId=300, ancestors="0,100,300")
```

| 员工 | 员工 dept_id | 设备 A (deptId=100, 总公司) | 设备 B (deptId=200, 研发部) | 设备 C (deptId=300, 市场部) |
|------|------------|---------------------------|---------------------------|---------------------------|
| 张三 | 201 (前端组) | ✅ 可见 | ✅ 可见（子部门） | ❌ 不可见 |
| 李四 | 202 (后端组) | ✅ 可见 | ✅ 可见（子部门） | ❌ 不可见 |
| 王五 | 300 (市场部) | ✅ 可见 | ❌ 不可见 | ✅ 可见 |

**关键结论**：
- 为总公司（deptId=100）的设备录入人脸后，所有子公司/部门的设备都能通过同步获取到
- 为研发部（deptId=200）的设备录入人脸后，只有总公司设备和研发部及其子部门的设备能获取到，市场部设备看不到
- 权限范围是**自顶向下包含**的树形结构，上游设备能看到下游数据，平行部门互不可见

### 4.4 全量同步 vs 增量同步

| 场景 | `lastSyncTime` | 返回内容 | syncAction |
|------|---------------|---------|------------|
| 终端首次启动/本地数据清空 | `0` | 所有 `status='0'` 的活跃记录（按设备部门树过滤） | 全部 `ADD` |
| 终端定期同步 | 上一次 `syncVersion` | 该时间后变更的记录（含 `status='0'` 新增和 `status='9'` 删除） | `ADD` 或 `DELETE` |

### 4.5 终端处理 syncAction 逻辑

```
if (syncAction == "ADD" && status == "0"):
    解析 faceAiId 获取 employeeId 和 faceId
    将 faceFeature 注册/更新到本地 FaceAI 底库
    如有 faceImageBase64 则缓存图片

if (syncAction == "DELETE" && status == "9"):
    从本地 FaceAI 底库中移除 faceAiId 对应的特征
    删除本地缓存的图片文件
```

### 4.6 分页同步流程

```
lastSyncTime = 本地存储的上次 syncVersion
page = 0

loop:
    发送 syncFaceData { lastSyncTime, page, pageSize, includeFlags }
    接收响应 { hasMore, syncVersion, page, faceFeatures }
    逐条处理 faceFeatures（按 syncAction 新增/删除本地底库）
    if hasMore:
        page = page + 1
    else:
        存储 syncVersion 到本地
        break
```

## 五、多设备同步场景

### 5.1 核心机制：Push 通知 + 增量拉取（Pull）

管理员录入/删除人脸时，服务端立即通过 MQTT 向所有**有部门权限且在线**的设备推送 `faceChanged` 通知（Push）。终端收到通知后立即触发增量同步拉取具体数据（Pull）。离线设备在其下次上线后的定时同步周期中自动补齐。

```
Admin 录入/删除人脸
    │
    ├─ 1. 写入数据库
    │
    ├─ 2. 反查有权限的在线设备（部门树过滤）
    │      SELECT d.* FROM biz_device d
    │      WHERE d.status='0' AND d.online_status='1'
    │        AND (d.dept_id = #{deptId}
    │             OR find_in_set(d.dept_id, 
    │                 (SELECT ancestors FROM sys_dept WHERE dept_id=#{deptId})))
    │
    └─ 3. MQTT Push: 逐个设备发送 faceChanged 通知
           Topic: card/{deviceId}/down
           Payload: {"cmd":"faceChanged","data":{"employeeId":10001,"faceId":52,"changeType":"ADD","timestamp":...}}

各设备收到 faceChanged → 立即增量同步 → 秒级获取新人脸
```

```
设备 A (deptId=100)  ──定时(如5min)──→ MQTT: syncFaceData{lastSyncTime=T1, page:0}
                                       ← syncFaceDataResp{hasMore=true, faceFeatures:[新增/删除]}

设备 B (deptId=200)  ──定时(如5min)──→ MQTT: syncFaceData{lastSyncTime=T2, page:0}
                                       ← syncFaceDataResp{hasMore=true, faceFeatures:[新增/删除]}

设备 C (deptId=300)  ──定时(如5min)──→ MQTT: syncFaceData{lastSyncTime=T3, page:0}
                                       ← syncFaceDataResp{hasMore=false}（无变更）
```

### 5.2 管理员在 Web 端录入 → 多设备同步

```
时间线:
  T0: 管理员为员工张三(dept_id=201)录入人脸
      → 数据库写入 faceId=52, update_time=T0
      → 服务端反查有权限的在线设备: [设备A(deptId=100), 设备B(deptId=200)]
      → MQTT Push faceChanged 通知到设备A、设备B
  
  T0+1s: 设备A(deptId=100, 总公司) 收到 faceChanged{employeeId:10001, faceId:52, changeType:"ADD"}
      → 触发增量同步: syncFaceData{lastSyncTime=上次同步时间}
      → 返回: faceAiId="10001_52", syncAction="ADD"
      → 设备A注册到底库
  
  T0+2s: 设备B(deptId=200, 研发部) 收到 faceChanged{employeeId:10001, faceId:52, changeType:"ADD"}
      → 触发增量同步
      → 返回: faceAiId="10001_52", syncAction="ADD"
      → 设备B注册到底库
  
  设备C(deptId=300, 市场部): deptId 300 不在 dept 201 的祖级链中 → 不会被通知
      → 定时同步时也不返回此人脸（无权限）
```

### 5.3 设备 A 录入人脸 → 设备 B/C 同步

```
时间线:
  T0: 设备A(deptId=100)现场采集员工李四人脸
      → 本地 FaceAI 注册
      → POST /api/v1/employee/face（HTTP上报到Gateway）
      → 数据库写入 faceId=55, update_time=T0
  
  T1: 设备B(deptId=200, 研发部) 定时同步
      → 增量拉取到 faceId=55
      → 注册到本地底库
  
  T2: 设备D(deptId=400, 其他部门) 定时同步  
      → 如果李四在部门400或400的子部门下 → 同步到
      → 如果李四不在 → 不同步
```

### 5.4 删除人脸 → 多设备同步

```
时间线:
  T0: 管理员删除 faceId=52
      → 数据库 update_time=T0, status='9'
  
  T1~TN: 所有有权限的设备(总公司+研发部+前端组+后端组)下次定时同步
      → 增量拉取到 faceId=52, syncAction="DELETE"
      → 各设备从本地 FaceAI 底库注销
```

### 5.5 双通道保障

| 通道 | 延迟 | 机制 | 适用 |
|------|------|------|------|
| **Push 通知** | 秒级 | MQTT `faceChanged` → 设备立即增量同步 | 在线设备实时感知 |
| **Pull 定时同步** | 5 分钟 | 定时 `syncFaceData` 增量拉取 | 离线设备补齐、兜底保障 |

> **推荐**：定时同步保持 5 分钟周期作为离线兜底。正常场景下，在线设备通过 Push 通知即可实时感知，无需缩短定时周期。

### 5.6 终端自己录入（人脸采集一体机）

```
终端采集 → 本地 FaceAI 提取特征 → 
  ├─ POST /api/v1/employee/face（HTTP 上报到 Gateway）→ 数据库
  └─ 本地底库注册: FaceAI.register(faceAiId, faceFeature)
```

其中 `faceAiId` 需要等待服务端返回 `faceId` 后才能确定。建议流程：

```
1. POST /api/v1/employee/face → 服务端返回 faceId
2. faceAiId = employeeId + "_" + faceId
3. FaceAI.register(faceAiId, faceFeature)
```

## 六、关键注意事项

### 6.1 字段变更

| 变更项 | 旧值 | 新值 | 影响 |
|--------|------|------|------|
| FaceAI 注册 ID | `10001` | `10001_52` | 终端需适配解析逻辑 |
| 员工-人脸关系 | 唯一条记录 | 可能多条 | 底库需支持多记录存储 |
| 同步返回 `syncAction` | 不支持 | `ADD` / `DELETE` | 终端需根据此字段区分操作 |

### 6.2 文件哈希去重

服务端基于 `fileHash`（SHA-256）做**全局去重**——同一张图片不能给任何员工重复录入。如果终端采集了同一张图片需要录入给不同员工，服务端会拒绝（返回 "该人脸图片已存在"）。

### 6.3 每人上限

默认每人最多 **3张** 人脸图片，由配置项 `system.face.maxPerEmployee` 控制（可在 `application.yml` 中调整）。达到上限后调用录入接口会返回错误。

### 6.4 删除行为

- 删除是**软删除**（`status` → '9'），数据不物理删除
- 终端不需要通过 MQTT 实时通知来感知删除
- 终端在**增量同步**时会收到 `syncAction=DELETE` 的记录，据此从本地底库注销
- 删除后，`faceRegistered` 仍为 "1"（直到该员工所有活跃人脸都被删除）

### 6.5 同步时机建议

| 场景 | 同步类型 | 说明 |
|------|---------|------|
| 终端首次安装/数据清空 | 全量同步 | `lastSyncTime=0` |
| 收到 MQTT `faceChanged` 通知 | 立即增量同步 | 使用上次存储的 `syncVersion`，优先处理 |
| 终端定时任务（建议 5 分钟兜底） | 增量同步 | 离线设备上线后补齐 |
| MQTT 不可用时 | HTTP 降级 | `POST /api/v1/employee/face/sync`，格式一致 |

### 6.6 资源文件域名

图片访问 URL（`url` 和 `faceImageUrl`）由服务端 `ruoyi.resourceUrl` 配置决定。在 API 与静态资源分离部署的场景下，服务端配置的 `resourceUrl` 可能不是当前请求的域名。**终端直接使用服务端返回的完整 URL 即可，无需自行拼接**。

## 八、多设备同步架构详解

### 8.1 当前架构：Push 通知 + Pull 补齐（混合模式）

```
                    ┌─────────────────────────────────────────┐
                    │              Admin Server                 │
                    │  ┌──────────────────────────────────────┐│
                    │  │ BizEmployeeController                 ││
                    │  │  addFaceFeature() → DB WRITE          ││
                    │  │    → 反查有权限在线设备                  ││
                    │  │    → MQTT Push: faceChanged            ││
                    │  │  softDeleteFaceFeature()              ││
                    │  │    → 同样流程 (changeType=DELETE)       ││
                    │  └──────────────────────────────────────┘│
                    └───┬───────────────────┬──────────────────┘
                        │ Push              │ Push
                        ▼                   ▼
              ┌──────────────┐    ┌──────────────┐    无权限 → 不通知 ✗
              │ 设备A (总)    │    │ 设备B (研发)  │    ┌──────────────┐
              │ deptId=100   │    │ deptId=200   │    │ 设备C (市场)  │
              │ ✅ faceChanged│   │ ✅ faceChanged│   │ deptId=300   │
              │ → 立即同步    │    │ → 立即同步    │   │ 无权获取      │
              └──────┬───────┘    └──────┬───────┘    └──────┬───────┘
                     │                   │                    │
                     ▼                   ▼                    ▼
              ┌──────────────────────────────────────────────────┐
              │             MySQL (biz_face_feature)              │
              │  设备 Pull syncFaceData 拉取具体数据                  │
              └──────────────────────────────────────────────────┘
```

**已实现逻辑**：
1. Admin 录入/删除人脸 → 写入数据库
2. 根据员工 `dept_id` 反查所有有权限的在线设备（部门树过滤）
3. 逐个设备发送 MQTT `faceChanged` 通知（Push）
4. 设备收到通知后立即触发 `syncFaceData` 增量同步（Pull）
5. 离线设备通过定时同步（5分钟）自动补齐

### 8.2 部门树权限实现细节

#### 数据表结构

```
biz_employee                   sys_dept
┌──────────────┐              ┌──────────────────────────┐
│ employee_id  │              │ dept_id  │ ancestors       │
│ dept_id ─────┼──────┐       │ 100      │ "0,100"          │
│ name         │      │       │ 200      │ "0,100,200"      │
└──────────────┘      │       │ 201      │ "0,100,200,201"  │
                      │       │ 300      │ "0,100,300"      │
biz_device            │       └──────────────────────────┘
┌──────────────┐      │
│ device_id    │      │
│ dept_id ─────┼──────┘
│ device_name  │
└──────────────┘
```

#### 权限判定 SQL

服务端 Mapper XML 中的核心过滤逻辑：

```sql
-- 查询某设备(deptId=200)有权限看到的人脸特征
SELECT ff.* FROM biz_face_feature ff
WHERE ff.status = '0'
  AND ff.employee_id IN (
    -- 子查询1: 找到"设备deptId及其所有子部门"中的员工
    SELECT e.employee_id FROM biz_employee e
    WHERE e.dept_id IN (
      -- 子查询2: 设备部门 + 所有子部门
      SELECT d.dept_id FROM sys_dept d
      WHERE d.dept_id = 200                    -- deptId=200(研发部)自身
         OR find_in_set(200, d.ancestors)      -- 祖先中包含200的子部门(前端组、后端组)
    )
  )
```

**`find_in_set` 示例**（MySQL 内置函数）：
- `find_in_set(200, "0,100,200,201")` → 返回 3（位置3，即匹配）
- `find_in_set(200, "0,100,300")` → 返回 0（未找到）

#### 三种典型场景

```
场景1: 总公司设备同步
  deptId=100 → 查询所有 dept_id=100 或 ancestors 含 "100" 的部门
             → 返回: [100总公司, 200研发部, 201前端组, 202后端组, 300市场部]
             → 能看到所有部门的人脸 ✅

场景2: 研发部设备同步
  deptId=200 → 查询所有 dept_id=200 或 ancestors 含 "200" 的部门
             → 返回: [200研发部, 201前端组, 202后端组]
             → 能看到研发部及子部门的人脸 ✅
             → 看不到市场部的人脸 ❌

场景3: 员工在多个不同部门
  张三 dept_id=201 → 总公司设备✅  研发部设备✅  市场部设备❌
  李四 dept_id=202 → 总公司设备✅  研发部设备✅  市场部设备❌
  王五 dept_id=300 → 总公司设备✅  研发部设备❌  市场部设备✅
```

### 8.3 `faceChanged` MQTT 通知协议

- **Topic（下行）**：`card/{deviceId}/down`
- **cmd**：`faceChanged`
- **触发时机**：管理员通过 Web 后台录入或删除人脸时

**通知体**：

```json
{
  "cmd": "faceChanged",
  "msgId": "msg_xxx",
  "data": {
    "employeeId": 10001,
    "faceId": 52,
    "changeType": "ADD",
    "timestamp": 1722585600000
  }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `employeeId` | Long | 变更涉及的员工ID |
| `faceId` | Long | 变更的人脸记录ID |
| `changeType` | String | `"ADD"` = 新增，`"DELETE"` = 删除 |
| `timestamp` | Long | 变更时间戳（毫秒） |

**终端处理**：

```
收到 faceChanged:
    → 立即触发 syncFaceData 增量同步
    → 根据 syncAction 新增/删除本地底库
    → 无需解析通知体中的数据字段（通知仅作触发用途）
```

### 8.4 实现细节：Controller 侧

`BizEmployeeController` 中新增的 `notifyFaceChanged()` 方法：

```java
private void notifyFaceChanged(BizEmployee employee, Long faceId, String changeType) {
    // 1. 反查有权限的在线设备（部门树过滤）
    List<BizDevice> devices = deviceService.selectPermittedDevicesForEmployee(employee.getDeptId());

    // 2. 逐个设备发送 faceChanged MQTT 通知
    for (BizDevice device : devices) {
        adminMqttClient.publishCommand(
            device.getDeviceId(),
            device.getDeviceCode(),
            "faceChanged",
            data,      // {employeeId, faceId, changeType, timestamp}
            operator
        );
    }
}
```

- `selectPermittedDevicesForEmployee` 使用部门树反向查找：只通知 `dept_id` 是员工部门祖先（或自身）的设备
- 仅通知 `online_status='1'` 的在线设备
- 单设备推送失败不影响其他设备（warn 日志记录、不抛异常）
