# 串口高频接收与实时性优化方案

## 1. 背景与结论

实机 CPU 采样显示，`SerialReadThread` 长时间占用约 35%–79% CPU，同时应用主进程和渲染线程也持续高占用。管理员密码验证的 SQLite 日志中，已观察到的两次查询耗时约 13ms、146ms，不能证明 SQLite 是导致接近一分钟卡顿的主因。

当前优先问题是：高频轮询数据在串口接收、完整 HEX 日志、协议路由、主线程事件、WebView 渲染和 SQLite 缓存之间重复传播，挤压了正常交互和开门应答处理。

本方案的目标是：**保持串口和开门应答实时，合并重复状态通知，异步批量持久化，避免普通状态流量阻塞关键操作。**

## 2. 不变规则

- 串口物理接收必须持续进行，不能因页面、SQLite 或 MQTT 状态上报暂停。
- 开门 `0x11` / `0x12`、串口错误、CRC 异常和目标卡槽状态确认属于关键事件，必须立即处理。
- 正在等待开门应答时，不发送新的轮询命令；但接收线程仍持续读取和解析数据。
- 取卡、管理员取卡、人脸取卡、后台取卡和远程开门的业务成功语义仍由 Vue 业务层决定；Android 串口层不得新增第二套业务真相。
- Android `DeviceCoreService` 只负责前台服务生命周期和原生串口能力的长期运行，不承担人员、卡槽业务、SQLite 业务数据或 MQTT 业务结果判断。
- 未确认的串口地址、轮询拓扑和协议字段不在本方案中新增或推断。

## 3. 为什么不能“每次接收后休眠 100ms”

不能在每次读取到有效数据后执行 `sleep(100ms)`，原因如下：

- 多帧连续返回时会造成接收积压；
- 开门 `0x11` / `0x12` 会被人为延迟，增加 300ms 应答窗口超时风险；
- 粘包、拆包的帧组装时机被推迟；
- 这只能掩盖 CPU 根因，不能减少 HEX 转换、日志、跨线程事件和重复写库。

可以使用短暂退避，但只用于底层读取连续返回空数据的异常忙循环：

- 有效数据：立即处理，不休眠；
- `read()` 返回 `0`：连续空读时退避 5–10ms；
- I/O 异常或关闭：退出读线程，按既有连接恢复策略处理。

## 4. 目标链路

```text
Android DeviceCoreService（前台服务，长期持有串口能力）
  └─ SerialReadThread：阻塞读取 / 空读退避
       └─ 协议组帧、CRC 校验、帧分类
            ├─ 关键帧：立即交给命令等待者
            │    └─ 开门 ACK、失败标识、通信错误、关键确认
            └─ 普通状态帧：原生层按卡槽合并
                 └─ 每 100ms 推送一次“变化槽位集合”至 JsBridge
                      └─ Vue 更新 appState 页面投影
                           └─ SQLite 仅对变化槽位异步批量落盘
```

这里的 **100ms 是状态通知合并窗口，不是串口读取等待时间**。

## 5. 分层优化措施

### 5.1 串口接收与协议层：先降低 CPU

1. **关闭生产环境的逐帧完整 HEX 日志**
   - 默认仅记录计数、功能码、卡槽号和异常摘要。
   - 完整 HEX 仅在人工串口调试开关开启时记录。
   - 在转换 HEX 前先判断调试是否启用，避免“即使不打印也先构造字符串”。
   - CRC 错误、未知帧、开门 ACK 和明确故障帧可保留受限长度的完整报文。

2. **确保读取线程不忙等**
   - 使用阻塞读取作为正常路径。
   - 对连续 `read() == 0` 使用 5–10ms 空读退避。
   - 不对已读到的正常报文添加固定休眠。

3. **减少接收路径分配与装箱**
   - 避免每字节使用 `ArrayList<Byte>` 等装箱容器。
   - 避免为仅用于日志或后续丢弃的帧反复创建 HEX 字符串和 JSON。
   - 只在得到完整、CRC 合格的协议帧后进入业务事件分发。

### 5.2 原生状态合并：在进入主线程前削峰

以卡槽号为键维护短生命周期的 `latestChangedStatus`：

- 同一槽位在一个窗口内多次上报时，只保留最后一条；
- 与最近已发布状态完全相同的状态帧不向 WebView 转发；
- 每 100ms 最多发布一次有变化的槽位集合；
- 启动广播快照保留为一次完整快照，不与日常增量混淆；
- 关键 ACK、错误和开门目标的状态确认绕过合并窗口。

现有桥接层已有约 120ms 的状态合并。后续优化应把“无变化即丢弃”和“轻量状态合并”前移到原生协议事件进入主线程之前，避免主线程仍被大量相同状态帧唤醒。

### 5.3 命令与轮询：优先保障物理动作

串口写入保持唯一队列，采用明确优先级：

1. 开门、取卡、还卡等有 ACK 等待的物理命令；
2. 必要的失败重试；
3. 启动广播或明确的人工查询；
4. 常规分组或单槽轮询。

当物理开门命令在途时：

- 暂停**发送**新的轮询；
- 不暂停接收、组帧和关键应答匹配；
- 收到 `0x11`、`0x12` 或到达既有超时边界后，再恢复轮询；
- “无 `0x11` 但目标槽已确认空卡”的已确认业务规则，仍由 Vue 操作流程依据串口状态事件判定。

### 5.4 Vue 与 SQLite：显示优先、缓存降频

- Vue 收到变化槽位批次后立即更新页面投影；100–200ms 内可见的状态变化对用户而言是无感实时。
- SQLite 仅保存变化槽位，不为重复状态写入。
- 同一槽位在持久化窗口内只写最后状态；建议采用 250–500ms 的批量事务窗口。
- 开门结果、故障、操作记录等需恢复的关键事实可立即单独落盘，不等待普通状态批次。
- 状态上报、MQTT 和 outbox 使用已持久化的最新状态，不在串口接收线程同步执行。

## 6. 实时性边界

| 事件类型 | 是否合并 | 是否允许延迟 | 处理要求 |
| --- | --- | --- | --- |
| 串口原始字节接收 | 否 | 否 | 持续阻塞读取，空读才退避 |
| 帧组装、CRC 校验 | 否 | 否 | 在原生接收路径立即完成 |
| 开门 `0x11` / `0x12` | 否 | 否 | 立即匹配在途命令 |
| 开门目标槽状态确认 | 否 | 否 | 立即提供给操作流程 |
| CRC/通信故障 | 否 | 否 | 立即产生受限错误事件 |
| 普通卡槽状态变化 | 是 | 最多约 100ms | 仅推送变化槽位集合 |
| 无变化的重复状态 | 是 | 不适用 | 不转发、不刷新、不写库 |
| SQLite 卡槽快照 | 是 | 250–500ms | 异步批量、每槽保留最终值 |
| MQTT 状态上报 | 是 | 按现有配置 | 不能阻塞串口或 UI |

## 7. 实施顺序

### 第一阶段：止血与定位

1. 关闭生产环境逐帧 HEX 与逐帧路由日志，保留调试开关。
2. 为串口接收增加非敏感指标：读取次数、空读次数、有效字节数、完整帧数、CRC 失败数、丢弃的重复状态数、队列长度。
3. 排查并修复 `read() == 0` 的忙等；不改变有效数据读取节奏。
4. 复测 `SerialReadThread`、主进程和 `RenderThread` CPU。

### 第二阶段：原生侧事件削峰

1. 在协议事件进入主线程前，按卡槽比较并丢弃重复状态。
2. 将变化状态按 100ms 窗口合并后再跨桥。
3. 保证 ACK、错误和命令确认事件绕过状态合并。
4. 验证拆包、粘包、多段返回和开门期间状态帧不会丢失关键语义。

### 第三阶段：Vue 缓存与体验优化

1. UI 继续即时消费状态批次，不等待 SQLite。
2. SQLite 对变化状态进行异步批量写入。
3. 管理员验证只依赖本地凭据查询与哈希校验，不被状态流量和全量快照写入挤压。
4. 复测管理员登录、管理员取卡、人脸取卡、后台单槽取卡、后台一键取卡和远程开门。

## 8. 验收标准

- 空闲轮询时，`SerialReadThread` 不再长期占用单核的大比例 CPU；不存在持续空读忙循环。
- 无状态变化时，页面不反复刷新，SQLite 不产生重复写入。
- 有状态变化时，页面在 100–200ms 内更新。
- 开门 ACK 不受状态合并、SQLite 事务、MQTT 上报或页面渲染阻塞。
- 等待开门应答时不再发送新的轮询命令。
- 管理员密码输入完成后，在稳定运行状态下应在约 1 秒内返回正确结果或明确错误，不出现长时间“正在验证”。
- 调试模式关闭后，不再输出每个状态帧的完整 HEX；开启调试时仍可获得必要的串口诊断信息。
- 100 卡槽连续轮询、状态变化、开门和页面操作同时进行时，应用仍可正常点击、切页和完成管理员验证。

## 9. 不在本方案内的事项

- 不修改串口协议功能码、CRC 算法、卡槽地址映射或未确认的轮询拓扑。
- 不将卡槽业务真相、取卡成功判断或 Vue SQLite 表迁移到 Android Service。
- 不以降低轮询频率替代接收侧 CPU 优化；轮询周期只能依据实机协议和体验验证单独调整。
- 不把设备物理串口接收迁移到后端服务器；后端只接收设备端汇总后的状态与操作结果。

## 10. 后端协作确认项

- 后端状态上报是否接受“只上报变化状态 + 定时完整快照”的组合；当前客户端必须继续遵守已确认的取卡后完整 `statusReport` 规则。
- 后端是否需要区分：单板 ACK、目标槽状态确认、客户端操作完成、状态上报完成。
- 后端远程开门是否接受“已受理、正在逐槽开门”的早期回执，以及后续状态上报反映最终物理结果。
- 串口调试日志是否只在临时开关期间上报，避免 MQTT `logReport` 自身形成额外压力。
