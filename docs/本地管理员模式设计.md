# 本机管理员权限模型设计 V2

## 1. 背景与目标

### 1.1 架构约束

当前设备端采用 V2 三层架构：

- **Vue 层**：业务状态、SQLite 缓存、本机权限控制
- **Android 层**：仅提供 `storage.query` / `storage.execute` 等原生通道，不解释 Vue SQLite 业务表
- **`old/**`**：仅作历史参考，不恢复旧 Android 业务 Map 架构

### 1.2 业务需求

用户在首页匿名访问，点击管理员入口后只输入 6 位密码（无用户名），通过密码匹配到凭据 → 获得对应角色 → 获得对应权限。核心升级目标：

1. **角色可自定义**：不再绑定 3 个固定角色，支持 CRUD
2. **权限内容可自定义**：权限点可新增、编辑、分组
3. **用户可对应多角色**：一个凭据可绑定多个角色，权限取并集
4. **权限可继承**：角色可继承父角色的权限；权限点本身也可有层级（如 `cabinet.*` 包含 `cabinet.unlock`）

当前 UI 策略：角色编辑页只允许给角色分配已有权限点，不在该页暴露权限点新增/编辑/删除；如需开放权限点 CRUD，应另建独立权限点管理页。

### 1.3 访问控制原则

| 页面类型 | 权限要求 |
|---------|---------|
| `/pages/index/index`（首页） | 匿名可访问 |
| `/pages/splash/splash`（启动页） | 匿名可访问 |
| 所有管理页 | 必须持有对应权限点的有效 session |
| 危险操作（弹卡/重启/升级等） | 页面守卫 + 动作执行前二次校验 |

- `app/.../NativeAuthManager.java`：三角色 `SYSTEM_ADMIN` / `OPS` / `DEVELOPER`，密码 `111111` / `222222` / `333333`，裸 SHA-256（本设计重构为 RBAC 二角色 + 可自定义，弃用此实现）

## 4. 数据模型

### 4.1 ER 关系

```
local_roles ──(N:M)── local_role_permissions ──(N:M)── local_permissions
     │                                                      │
     │ parent_role_id (自引用)                               │ parent_key (自引用)
     │                                                      │
     │ (N:M)                                                │
local_credential_roles                                      │
     │                                                      │
local_auth_credentials  ─────────────────────────────────────┘
     │
local_auth_session (单行, session_key='current')
```

### 4.2 角色表 `local_roles`

```sql
CREATE TABLE IF NOT EXISTS local_roles (
  role_id        TEXT PRIMARY KEY,
  role_name      TEXT NOT NULL UNIQUE,
  parent_role_id TEXT,           -- 继承父角色, NULL = 顶级
  is_system      INTEGER NOT NULL DEFAULT 0,  -- 1 = 系统内置, 不可删除
  is_enabled     INTEGER NOT NULL DEFAULT 1,
  sort_order     INTEGER NOT NULL DEFAULT 0,
  description    TEXT NOT NULL DEFAULT '',
  created_at     INTEGER NOT NULL,
  updated_at     INTEGER NOT NULL
);
```

**继承规则**：角色 A 设置 `parent_role_id = B`，A 的有效权限 = A 自身权限 ∪ B 有效权限（递归）。解析时必须检测环，有环时拒绝保存并报配置错误。

**`is_system` 规则**：
- `is_system = 1` 的角色不可删除，不可修改 role_id
- 可修改名称、权限分配、父角色（但父角色应防止形成环）

### 4.3 权限点表 `local_permissions`

```sql
CREATE TABLE IF NOT EXISTS local_permissions (
  permission_key  TEXT PRIMARY KEY,       -- 如 cabinet.unlock
  parent_key      TEXT,                   -- 如 cabinet.* 或 NULL
  permission_name TEXT NOT NULL,
  category        TEXT NOT NULL DEFAULT '',-- 分组: cabinet / auth / upgrade / biometric / debug / admin
  sort_order      INTEGER NOT NULL DEFAULT 0,
  description     TEXT NOT NULL DEFAULT '',
  created_at      INTEGER NOT NULL
);
```

**层级规则**：`parent_key` 支持通配符式的权限父节点。例如 `cabinet.*` 作为父节点，其下包含 `cabinet.unlock`、`cabinet.unlockAll` 等叶子权限。解析时从叶子向上递归展开。

树形示例：

```
*                              ← 通配，全部权限
├── admin.manage               ← 管理角色/凭据/权限（最高敏感度）
├── system.menu                ← 系统设置入口页
├── management.menu            ← 管理功能入口页
├── cabinet.*                  ← 卡柜通配
│   ├── cabinet.view           ← 查看卡状态
│   ├── cabinet.unlock         ← 单门开门
│   └── cabinet.unlockAll      ← 一键弹卡
├── auth.password.manage       ← 修改密码
├── app.restart                ← 重启应用
├── settings.basic             ← 基本设置
├── settings.advanced          ← 高级参数设置
├── upgrade.*                  ← 升级通配
│   ├── upgrade.app            ← APP 升级
│   └── upgrade.firmware       ← 固件/单板/主板升级
├── biometric.register         ← 人脸 / 指纹注册
├── employee.view              ← 人员管理（查看）
├── employee.edit              ← 人员管理（编辑）
├── unit.view                  ← 单元管理
├── history.view               ← 历史管理
├── authorization.manage       ← 系统授权
└── debug.command              ← 调试指令 / 工程模式
```

### 4.4 角色-权限关联表 `local_role_permissions`

```sql
CREATE TABLE IF NOT EXISTS local_role_permissions (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  role_id        TEXT NOT NULL,
  permission_key TEXT NOT NULL,
  created_at     INTEGER NOT NULL,
  UNIQUE(role_id, permission_key),
  FOREIGN KEY(role_id)        REFERENCES local_roles(role_id)        ON DELETE CASCADE,
  FOREIGN KEY(permission_key) REFERENCES local_permissions(permission_key) ON DELETE CASCADE
);
```

### 4.5 登录凭据表 `local_auth_credentials`

```sql
CREATE TABLE IF NOT EXISTS local_auth_credentials (
  credential_id   TEXT PRIMARY KEY,         -- UUID
  label           TEXT NOT NULL,            -- 凭据显示名, 如 "默认管理员"
  password_hash   TEXT NOT NULL,            -- PBKDF2-SHA256 结果 (hex)
  password_salt   TEXT NOT NULL,            -- 独立随机 salt (hex)
  password_state  TEXT NOT NULL DEFAULT 'INITIAL',  -- INITIAL / ACTIVE / EXPIRED
  enabled         INTEGER NOT NULL DEFAULT 1,
  failed_count    INTEGER NOT NULL DEFAULT 0,
  locked_until    INTEGER NOT NULL DEFAULT 0,  -- 锁定截止时间戳 (ms), 0 = 未锁定
  ttl_seconds     INTEGER NOT NULL DEFAULT 3600,-- 会话 TTL 时长 (秒), 默认 1 小时
  created_at      INTEGER NOT NULL,
  updated_at      INTEGER NOT NULL
);
```

**重要变更**：移除了原来表中 `role_id TEXT NOT NULL` 的单外键字段。凭据与角色的关联改为通过 `local_credential_roles` 多对多实现。

### 4.6 凭据-角色关联表 `local_credential_roles`

```sql
CREATE TABLE IF NOT EXISTS local_credential_roles (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  credential_id  TEXT NOT NULL,
  role_id        TEXT NOT NULL,
  UNIQUE(credential_id, role_id),
  FOREIGN KEY(credential_id) REFERENCES local_auth_credentials(credential_id) ON DELETE CASCADE,
  FOREIGN KEY(role_id)       REFERENCES local_roles(role_id)             ON DELETE CASCADE
);
```

### 4.7 登录会话表 `local_auth_session`

```sql
CREATE TABLE IF NOT EXISTS local_auth_session (
  session_key    TEXT PRIMARY KEY,     -- 固定 'current'
  credential_id  TEXT NOT NULL,
  role_ids       TEXT NOT NULL,        -- 逗号分隔, 如 "SUPER_ADMIN,OPS"
  login_at       INTEGER NOT NULL,
  expires_at     INTEGER NOT NULL,     -- 绝对过期时间戳 (ms); 页面跳转时刷新
  ttl_seconds    INTEGER NOT NULL,     -- 创建凭据时设置的默认 TTL 时长
  updated_at     INTEGER NOT NULL
);
```

**重要约束**：
- `session` 表示**不存储 `permissions_json`**，避免权限快照成为第二套真相
- `role_ids` 仅用于日志追溯；**所有鉴权必须实时查询 SQLite**
- **TTL 机制**：`expires_at` 为绝对过期时间，页面跳转（路由变化）时向前滚动一个 `ttl_seconds`；超时后自动清退到首页
- **启动即清**：App/WebView 启动时无条件清理 session，即重启 App = 退出管理员模式
- `ttl_seconds` 来源：创建凭据时设置，存于 `local_auth_credentials.ttl_seconds`（默认如 3600 秒），创建后可修改

### 4.8 二级密码表 `local_secondary_password`

```sql
CREATE TABLE IF NOT EXISTS local_secondary_password (
  id             INTEGER PRIMARY KEY CHECK (id = 1), -- 永远只有 1 行
  password_hash  TEXT NOT NULL,             -- PBKDF2-SHA256 (salt:hash)
  password_salt  TEXT NOT NULL,             -- 独立随机 salt
  updated_at     INTEGER NOT NULL
);
```

**约束**：
- 全表只允许 1 行（`CHECK id = 1`），存储唯一的"管理页二级密码"
- 初始化时写入默认密码 `123456` 的 hash
- 修改二级密码：校验旧密码 → 生成新 hash+新 salt → `UPSERT id=1`
- 与 `local_auth_credentials` 完全隔离，二级密码不绑定任何角色

## 5. 密码规则

| 规则 | 说明 |
|-----|------|
| 密码格式 | 严格 6 位数字 |
| 唯一性 | 不同凭据的密码**必须**不同（只输密码识别身份的前提） |
| KDF 算法 | PBKDF2-SHA256，迭代次数 ≥ 100,000 |
| Salt | 每个凭据独立随机 salt（crypto.getRandomValues 生成 16 字节） |
| 哈希存储格式 | `salt_hex:hash_hex` 或分列存储 |
| 锁定策略 | 连续失败 5 次 → `locked_until = now + 5分钟` |
| 首次登录 | `password_state = 'INITIAL'` 的凭据登录后**强制跳转修改密码页**，不修改则无法进入管理功能 |
| 密码复杂度 | 允许简单密码（如 `111111`），不作复杂度要求 |

**首次登录强制修改流程**：

```
密码登录成功 → 查 credential.password_state
  ├── = 'ACTIVE' → 进入管理功能
  └── = 'INITIAL' → 重定向到密码修改页
                    → 必须修改密码后才能访问管理页
                    → 修改成功 → password_state = 'ACTIVE'
```

**与远程认证的关系**：

本机管理员登录(`loginLocal`)是**纯离线本地操作**。后端**不存在** `POST /auth/login` 远程认证接口，`services.loginLocal` 为唯一管理员认证入口。

## 6. 登录与身份校验流程

### 6.1 完整登录流程

```
首页 index 匿名访问
  │
  ├─ 点击管理员入口 icon
  │     └─ 弹出 PasswordModal（6 位数字键盘）
  │
  ├─ 用户输入密码并确认
  │     │
  │     └─ services.loginLocal(password)
  │           │
  │           ├─ 1. 确保 SQLite 权限表已初始化（无表则 seed 默认数据）
  │           │
  │           ├─ 2. SELECT * FROM local_auth_credentials WHERE enabled = 1
  │           │
  │           ├─ 3. 遍历凭据:
  │           │     ├─ 检查 locked_until > now → 跳过（加锁消息稍后统一返回）
  │           │     ├─ PBKDF2(password, credential.salt) → 与 password_hash 比对
  │           │     └─ 命中 → 加入 matched[] 列表
  │           │
  │           ├─ 4. 匹配结果判断:
  │           │     ├─ matched.length === 0 → 所有凭据 failed_count++ → 提示"密码错误"
  │           │     ├─ matched.length === 1 → 正常登录
  │           │     └─ matched.length  > 1 → 配置错误 → 禁止登录 → 返回错误
  │           │
  │           ├─ 5. 登录成功:
  │           │     ├─ 重置 failed_count = 0, locked_until = 0
  │           │     ├─ 查询 local_credential_roles → roleIds[]
  │           │     ├─ resolveEffectivePermissions(roleIds) → Set<permission_key>
  │           │     ├─ 读取 credential.ttl_seconds → 计算 expires_at = now + ttl_seconds * 1000
  │           │     ├─ DELETE+INSERT local_auth_session (session_key='current')
  │           │     ├─ appState.session = { credentialId, roles, permissions: Set, ttlSeconds }
  │           │     └─ 若 password_state = 'INITIAL' → 设置 needsPasswordChange: true
  │           │
  │           └─ 返回 { success: true, roles, permissions, needsPasswordChange, ttlSeconds }
  │
  └─ uni.navigateTo('/pages/admin/admin')
```

### 6.2 有效权限解析算法

```
输入: roleIds (Array<string>)
输出: Set<permission_key> (叶子权限集)

function resolveEffectivePermissions(roleIds):
  expandedRoles = new Set()
  
  // 第1步: 展开角色继承链
  for each roleId in roleIds:
    chain = resolveRoleChain(roleId)  // BFS/DFS 沿 parent_role_id 向上
    expandedRoles.addAll(chain)
  
  // 第2步: 收集所有直接分配的权限
  rawPermissions = new Set()
  for each roleId in expandedRoles:
    rows = SELECT permission_key FROM local_role_permissions WHERE role_id = roleId
    rawPermissions.addAll(rows)
  
  // 第3步: 展开权限层级（通配 → 叶子）
  leafPermissions = new Set()
  for each permKey in rawPermissions:
    leaves = expandPermission(permKey)  // 若为 cabinet.* → 展开为其所有子权限
    leafPermissions.addAll(leaves)
  
  return leafPermissions
```

**`expandPermission(key)` 逻辑**：

- 若 key 为叶子权限（`parent_key` 列中没有以它为 parent 的记录）→ 返回 `[key]`
- 若 key 为通配/父节点 → 递归查询所有 `parent_key = key` 的子权限，展开为叶子

例如：角色若被赋予 `cabinet.*`，`expandPermission('cabinet.*')` 返回 `['cabinet.view', 'cabinet.unlock', 'cabinet.unlockAll']`。

**缓存策略**：

`appState.session.permissions` 在内存中以 `Set` 形式存在，仅在 `loginLocal` / `logoutLocal` / App 重启时重建。运行时不刷新 SQLite 中的角色-权限变更（修改权限需退出重新登录才生效）。这是有意设计：避免中途权限变更导致正在操作中的用户界面陷入不一致。

### 6.3 鉴权判断

```js
// 单次权限判断
function hasPermission(permissionKey) {
  if (!appState.session?.permissions) return false
  return appState.session.permissions.has(permissionKey)
}

// 判断是否持有任意一个权限（用于菜单可见性）
function hasAnyPermission(...keys) {
  if (!appState.session?.permissions) return false
  return keys.some(k => appState.session.permissions.has(k))
}
```

**禁止的写法**：

```js
// ❌ 禁止：硬编码 role 名判断
if (appState.session.role === 'SYSTEM_ADMIN') { ... }

// ✅ 正确：走权限点
if (hasPermission('settings.advanced')) { ... }
```

## 7. TTL 会话管理与强制修改密码

### 7.1 TTL 到期自动清退

```js
// appState 或 router 守卫中启动 TTL 定时器
let ttlTimer = null

function startTtlTimer() {
  clearTtlTimer()
  const session = appState.session
  if (!session) return
  
  const remaining = session.expiresAt - Date.now()
  if (remaining <= 0) {
    forceLogout('会话已过期')
    return
  }
  
  ttlTimer = setTimeout(() => {
    forceLogout('会话已过期')
  }, remaining)
}

function clearTtlTimer() {
  if (ttlTimer) {
    clearTimeout(ttlTimer)
    ttlTimer = null
  }
}

function forceLogout(msg) {
  clearTtlTimer()
  appState.session = null
  uni.showToast({ title: msg || '登录已过期', icon: 'none' })
  uni.reLaunch({ url: '/pages/index/index' })
}
```

### 7.2 页面跳转刷新 TTL

在全局路由守卫中，每次页面跳转（非首页/启动页）时刷新 `expires_at`：

```js
// main.js 或 router 守卫
function onRouteChange(to) {
  const session = appState.session
  if (!session) return
  
  // 首页和启动页不刷新 TTL（匿名页，不应续期）
  if (to.path === '/pages/index/index' || to.path === '/pages/splash/splash') return
  
  // 刷新过期时间
  session.expiresAt = Date.now() + session.ttlSeconds * 1000
  
  // 同步到 SQLite
  localStore.updateSession({ expiresAt: session.expiresAt, updatedAt: Date.now() })
  
  // 重置定时器
  startTtlTimer()
}
```

### 7.3 启动即清

App/WebView 启动时（`services.init()` 或 `main.js onLaunch`）无条件执行：

```sql
DELETE FROM local_auth_session WHERE session_key = 'current';
```

同时 `appState.session = null`。重启 App 即清除所有登录状态，与 TTL 机制互补：

| 场景 | 触发机制 |
|------|---------|
| 不重启 App，TTL 到期 | `setTimeout` 到期 → `forceLogout` → `reLaunch` 首页 |
| 不重启 App，页面跳转 | 路由守卫刷新 `expires_at`，重置定时器 |
| 重启 App | 启动即清 → `DELETE` session + `appState.session = null` |

### 7.4 首次登录强制修改密码

`password_state = 'INITIAL'` 的凭据登录成功后，全局路由守卫拦截所有导航（除密码修改页）：

```js
// 登录成功后
if (needsPasswordChange) {
  // 直接跳转到修改密码页，跳过 admin 主页
  uni.redirectTo({ url: '/pages/admin/change-password?force=true' })
}

// 全局路由守卫中
function beforeRoute(to) {
  if (appState.session?.needsPasswordChange && to.path !== '/pages/admin/change-password') {
    uni.showToast({ title: '请先修改默认密码', icon: 'none' })
    uni.redirectTo({ url: '/pages/admin/change-password?force=true' })
    return false
  }
  return true
}
```

修改密码成功后：
- `password_state` 更新为 `'ACTIVE'`
- `needsPasswordChange` 标记清除
- 正常进入管理功能

### 8.2 页面守卫实现

#### 方案 A：路由配置（已采用）

在 `uniapp/src/pages.json` 无法直接注入守卫，需要在 `main.js` 中全局拦截：

```js
// uniapp/src/main.js
import { appState, hasPermission } from '@/state/appState.js'

// 页面权限映射
const PAGE_PERMISSIONS = {
  '/pages/admin/admin':             ['system.menu', 'management.menu', 'cabinet.view'],
  '/pages/system/system':           ['system.menu'],
  '/pages/management/management':    ['management.menu'],
  '/pages/card-status/card-status': ['cabinet.view'],
  '/pages/employees/employees':     ['employee.view'],
  '/pages/biometric/face':          ['biometric.register'],
  '/pages/biometric/fingerprint':   ['biometric.register'],
  '/pages/config/config':           ['settings.basic'],
  '/pages/feature/feature':         ['settings.advanced'],
  '/pages/engineering/engineering': ['debug.command'],
  '/pages/admin/role-manage':       ['admin.manage'],
  '/pages/admin/credential-manage': ['admin.manage'],
}

// 匿名页面白名单（不校验 session）
const PUBLIC_PAGES = new Set([
  '/pages/index/index',
  '/pages/splash/splash'
])

// 全局路由守卫
uni.addInterceptor('navigateTo', {
  invoke(args) {
    const path = args.url.split('?')[0]
    
    // 匿名页面放行
    if (PUBLIC_PAGES.has(path)) return true
    
    // 未登录 → 跳回首页 + toast
    if (!appState.session) {
      uni.showToast({ title: '请先登录', icon: 'none' })
      uni.reLaunch({ url: '/pages/index/index' })
      return false
    }
    
    // 权限校验
    const required = PAGE_PERMISSIONS[path]
    if (required) {
      const ok = required.some(p => appState.session.permissions.has(p))
      if (!ok) {
        uni.showToast({ title: '权限不足', icon: 'none' })
        return false
      }
    }
    
    return true
  }
})

// navigateBack / switchTab / reLaunch 同理
```

#### 方案 B：Mixin（轻量替代）

如果不想全局拦截，可在每个管理页的 `onShow` / `beforeMount` 中调用：

```js
// mixins/authGuard.js
export default {
  onShow() {
    if (!appState.session) {
      uni.showToast({ title: '请先登录', icon: 'none' })
      uni.reLaunch({ url: '/pages/index/index' })
      return
    }
    // 子组件通过 pagePermission 声明所需权限
    if (this.pagePermission && !hasPermission(this.pagePermission)) {
      uni.showToast({ title: '权限不足', icon: 'none' })
      uni.navigateBack()
    }
  }
}
```

采用**方案 A**（全局路由拦截），集中管理更安全，避免依赖每个页面开发者手动引入 mixin。

## 9. 动作级二次校验

|-----|------|------------------|
| 单门开门 | `cabinet.unlock` | `unlockSlot(slotId)` 第 1 行 |

// 使用

### 11.3 初始化时序

#### 系统凭据初始化

超级管理员和开发人员凭据都由 SQLite schema 初始化提供本机兜底，在线后台配置成功后改为后台权威密码：

```
splash.vue 启动流程
  → SQLite schema 初始化并确保 builtin:SUPER_ADMIN、builtin:DEVELOPER 兜底凭据和角色绑定存在
  → bootstrap 完成后、进入主页前 GET /api/v1/device/config
  → 校验完整 31 项设备配置
  → 同时提取后台超级管理员和 developerPassword，检查 6 位数字格式、彼此不同及自定义凭据唯一性
  → 单次 SQLite 写入以 PBKDF2 哈希整体覆盖两个系统凭据，password_state='ACTIVE'
  → 保存 runtimeConfig、configDraft、bootstrapConfig 后更新页面投影

MQTT syncConfig
  → 执行同一套完整配置校验、运行参数热更新保护和密码同步
  → 所有持久化成功后才回复 code=0；任一步失败回复 code=500
```

**设计意图**：
- 两个本机初始密码只用于后台配置尚未成功同步时避免设备锁死；不得把该兜底状态显示为后台已同步
- 后台配置是两个系统登录密码的权威来源，即使超级管理员曾在本机修改，下一次成功加载仍按后台值覆盖
- 两个后台系统密码可以接管彼此此前使用过的密码值，但同步后的两个值不得相同，也不得与自定义账号密码冲突
- 后台密码只在内存中用于校验和生成 PBKDF2 哈希；明文不得进入 `runtimeConfig`、`configDraft`、`bootstrapConfig`、页面投影或日志
- 任一字段缺失、格式非法、密码冲突或 SQLite 写入失败时保留原凭据；启动显示降级告警，MQTT `syncConfig` 返回失败

#### 开发人员系统账号约束

开发人员账号为本机内置凭据，默认创建 `builtin:DEVELOPER`，本机初始密码仅作为首次后台同步前的兜底。该账号仅用于开发/维护场景：

```
SQLite schema 初始化
  → 查询 builtin:DEVELOPER 是否存在
  → 不存在: INSERT local_auth_credentials (本机兜底密码 → PBKDF2 hash, password_state='ACTIVE', is_system=1)
           INSERT local_credential_roles (关联 DEVELOPER)
  → 已存在: 恢复系统角色绑定（不允许用户在界面中创建、删除或改绑开发人员账号）
在线配置同步
  → 读取 developerPassword 并以 PBKDF2 哈希覆盖 builtin:DEVELOPER
  → 普通界面仍不允许修改、删除、停用或改绑该账号
```

升级兼容：后台双系统密码同步前先排除两个系统凭据进行冲突检查，因此后台可交换或重新分配两个系统账号旧密码；如果任一后台密码命中自定义凭据，则整次同步失败并保留原系统凭据。

#### config 字段约定

后台系统超级管理员密码首选字段为 `superAdminPassword`，并兼容现有激活链已经使用的 `initialAdminPassword`、`initAdminPassword`、`adminInitialPassword`、`adminPassword`、`initialPassword`；这些字段只用于 `builtin:SUPER_ADMIN`。`developerPassword` 是 `builtin:DEVELOPER` 的独立必填字段，不作为超级管理员回退值。

**时序保证**：SQLite schema 初始化 → 创建/纠正两个系统兜底凭据及角色绑定；bootstrap 成功 → 启动加载完整后台配置并整体同步两个系统密码哈希 → 配置和凭据均持久化成功后进入正常投影。自定义管理员和管理二级密码不受后台密码字段影响。

### 12.4 二级密码

`admin.manage` 是最高敏感权限（可管理角色/凭据），进入角色管理和凭据管理页面时需**独立的二级密码**二次校验。

**特权角色豁免**：`SUPER_ADMIN` 和 `DEVELOPER` 为系统内置特权角色，**跳过二级密码校验**直接进入管理页。只有通过自定义角色获得 `admin.manage` 权限的凭据才需要二次校验。

#### 当前实现
默认值 `123456`，存储于 `local_secondary_password` 表（见 §4.8）：

```js
// localStore.js — 种子初始化
// PBKDF2-SHA256 hash of '123456' with random salt
seedSecondaryPassword(hash, salt)

// 特权角色列表（硬编码，不可通过角色管理修改）
const PRIVILEGED_ROLES = ['SUPER_ADMIN', 'DEVELOPER']
```

#### 校验流程
```
点击「角色管理」或「凭据管理」入口
  → 检查 appState.session.roles 是否包含 PRIVILEGED_ROLES 中任一角色
  → 是 → 跳过二级密码, 直接 navigateTo 目标页
  → 否 → 弹出二级密码输入框（6 位数字）
         → 查 local_secondary_password (id=1) 的 password_hash + password_salt
         → PBKDF2 比对
         → 匹配 → navigateTo 目标页
         → 不匹配 → 提示「二级密码错误」
```

#### 二级密码特点
- 与凭据登录密码分离，不存入 `local_auth_credentials`
- 独立存储在 `local_secondary_password` 专用表中，与凭据登录完全隔离
- 当前默认值为 `123456`
- 支持在二级密码校验页中**本地修改**（输入旧/新二级密码 → 本地更新存储）
- 不依赖 config 接口或其他外部下发
- `SUPER_ADMIN` / `DEVELOPER` 特权角色**豁免**二级密码；仅自定义角色需校验

## 14. 已识别风险

| # | 风险 | 缓解措施 |
|---|------|---------|
| 1 | 角色/权限编辑后不同步生效 | 设计上要求退出重新登录；管理页顶部提示"修改权限后请重新登录生效" |
| 2 | 误删最后一个管理员凭据致锁死 | `admin.manage` 凭据删除前检查；保留物理恢复机制（工程组合键恢复默认种子） |
| 3 | 角色继承产生环路 | 保存时 BFS/DFS 检测环，有环拒绝保存并提示用户 |
| 4 | `session.permissions` Set 与 SQLite 不同步 | 只在 loginLocal 时从 SQLite 计算一次；之后不自动刷新（有意设计） |
| 5 | 6 位数字密码暴力破解 | `failed_count` + 5 分钟锁定 + PBKDF2 高迭代次数增加单次耗时 |
| 6 | SQLite 不可用 | 禁止进入管理员模式，不回退 mock 或默认权限，仅提示"管理员模式不可用，请联系管理员" |
| 7 | 多个凭据密码相同导致无法识别身份 | 新增/修改凭据时检查全局密码唯一性 |
| 8 | 页面直接 URL 跳转绕过守卫 | 每个管理页 `onShow` 中主动检查 session + 权限 |

| 3 | 远程认证接口 | **不保留** | 服务器不存在 `POST /auth/login` 接口，`services.loginLocal` 为唯一本地认证入口 |
| 4 | 会话 TTL | **需要 TTL，同时保留「启动即清」** | 创建凭据时设置 `ttl_seconds` 默认值（非写死）。不重启 App 时 TTL 到期自动退回首页；页面跳转时刷新 TTL。重启 App 则所有登录状态无条件清除 |
| 5 | 管理页二级密码 | **本地设置 + 本地存储** | 存入独立的 `local_secondary_password` 表（永远 1 行），默认 `123456`（PBKDF2 hash）。支持在管理页中本地修改，不依赖 config 接口 |
