- 本文件适用于 `uniapp/**`，是该路径下比仓库根 `AGENTS.md`、`docs/**`、历史截图、历史实现和一般完成度清单更具体的客户验收约束。

- 只有当前实现违反本文件时，才能报告为“已完成功能发生回归”；不得把再次核对、恢复客户细节或补充回归测试描述成本轮新开发的功能。
- 完成度评估不得把客户明确删除的权限管理和黄色缓存提示横幅计入未完成项或完成度分母。
- 只有用户或客户在 2026-07-30 之后给出更明确的新要求，才能改变本文件的验收口径；不得根据旧 docs、旧版本或个人推断恢复已删除内容。

## 已确认的导航与页面布局

- 当前管理员导航树已经确认正确。后续任务不得根据旧文档重新增删、改名、重排或改回旧导航层级。
- 用户于 2026-08-02 最新确认管理员主页使用三列大卡片：圆形彩色图标居中在上、功能名称居中在下，不显示卡片说明和右侧箭头；实时状态的两个入口占同一三列网格的前两列。每个 Tab 下方不再重复显示 Tab 名称和说明，但系统管理内的业务分组标题保留。窄屏可降为两列，导航、权限、入口顺序和功能不得随样式调整改变。
- 系统授权和 MQTT 状态弹窗的内容区域使用弹窗卡片的完整可用宽度；历史页面的加载、错误和空状态与筛选区域同宽；卡状态页故障统计位于底部预留的右侧列。这些是已经完成的客户 UI 细节。
- 首页卡位区域不得恢复黄色“缓存状态”横幅，也不得为该横幅保留条件性空白或造成有提示、无提示时网格位置变化。后续若需要表达离线或旧数据，只能在客户另行确认展示方式后实现。
- 首页和卡状态页的卡柜网格必须使用同一个共享布局实现，并共同服从设备设置中的卡位总数、单组数量和排序方向；不得在任一页面重新硬编码列数、另写排序或形成第二套卡柜布局。
- 用户于 2026-08-07 最新确认：首页卡槽只展示状态，不响应点击且不弹出卡槽详情；卡实时状态页在共享卡槽卡片内直接展示卡号、在位/门锁、电压电流和故障摘要，维护人员无需逐个打开弹窗读取信息。实时状态页可保留点击后的管理员取卡操作，不得因此删除既有权限校验或物理确认流程。卡槽视觉按现场指示灯语义区分：充电中为红色、已充满为绿色、充电结束为橙色、故障为灰色、空卡为灰白色；离线、未知和非法卡继续使用中性灰阶并以文字标签区分。
- 用户于 2026-08-08 明确取卡选择以最新实时卡槽快照为唯一依据，不按员工同步卡号或指定卡号查槽。先从有卡且已充满/充电结束的卡槽中选择；只有全部有卡槽都在充电时，才按明确电量最高、缺少电量时按电压最高选择。最终卡号取自选中的物理卡槽，仅用于 operation、统计和上报。
- 用户于 2026-08-08 明确任何人取卡成功都立即上报完整 `statusReport`，不区分员工、管理员或远程操作。员工取卡以目标卡槽已开门/卡已弹出为成功；用户于 2026-08-14 最新明确管理员单槽取卡、本机/后台批量弹卡和 `remoteOpen` 以串口已接受开卡指令为成功，立即显示并播报“X号卡槽已开卡”，不再等待 `doorCode=1` 或空卡状态，MQTT 响应同样成功。批量弹卡每接受一个卡槽指令就上报一次；不得新增 Vue 轮询。上报失败写入既有 status outbox，不回滚已经完成的开卡指令；并发上报必须串行，不能丢弃较新的状态快照。
- 用户于 2026-08-08 明确后端新增 `mqttStatusReportInterval`，默认 `300000ms`，由 `scheduleStatusReport` 优先读取；旧 `slotStatusPushInterval` 仅作兼容回退。该字段只节流状态事件触发的上报，不得据此新增 Vue 卡槽轮询。

## 已确认的本机用户与密码规则

- 自定义管理用户、管理二级密码及其登录密码只保存在本机，不上传服务端后台；页面必须明确表达该事实。
- 用户于 2026-08-06 最终明确：系统内置超级管理员和开发人员登录密码都由后台配置管理，后台优先级高于本机。每次在线启动加载或 MQTT `syncConfig` 成功取得完整配置后，Vue 必须同时读取后台超级管理员密码和 `developerPassword`，校验后整体覆盖两个本机系统凭据；只允许把哈希写入 SQLite，明文不得进入配置缓存、页面投影或日志。任一字段缺失、格式非法、两者相同、与自定义凭据冲突或落库失败时必须保留原密码并明确返回失败，不得继续显示同步成功。两个后台系统密码允许重新分配彼此此前使用过的密码值。
- 开发人员账号仍是固定且不可由普通界面修改的系统内置账号，但其登录密码由后台 `developerPassword` 管理；本机初始值只作为首次成功同步前的兜底。不得在文档、日志或页面中暴露真实密码；不得允许普通新增、删除、停用、改绑或复制出第二个开发人员账号。
- 密码状态必须显示用户可理解的中文：`INITIAL` 为“使用初始密码，建议修改”，`ACTIVE` 为“正常”，`LOCKED` 为“已锁定”，`EXPIRED` 为“需要修改”；不得把原始枚举直接作为页面结果。
- 登录密码修改属于当前本机登录账号流程，不得误接到管理二级密码；成功后应保持或刷新有效登录会话，失败不得显示为成功。
- 超级管理员和开发人员拥有管理二级密码豁免，不要求再次输入，也不显示二级密码修改区域；其他具备管理资格的自定义管理员仍按现有二级密码验证流程执行。

## 已确认的角色与权限展示规则

- 开发人员角色是固定的系统内置角色，列表中必须灰显且不可选择、查看、编辑、停用或分配给其他账号；其权限范围对用户不可见。
- 用户于 2026-08-07 根据 BUG 管理表进一步明确：独立“权限管理”页面、入口和路由仍保持删除，但角色管理页必须恢复角色权限详情和自定义角色授权能力。点击非开发人员角色后使用右侧抽屉展示包含继承关系的有效权限；新增或编辑自定义角色时使用弹窗选择直接权限。
- 超级管理员角色允许在抽屉中只读查看全部权限，但与开发人员角色一样属于系统内置角色，不允许编辑、停用或删除。自定义角色才显示启停、编辑和删除操作。
- 用户于 2026-08-07 要求开发人员拥有全部功能权限；其系统角色固定授予 `*`，登录后必须能够进入账号管理、角色管理、设备、日志和全部已定义功能。BUG 表同一条备注又提出开发人员可编辑/删除，与 BUG-006 的“开发人员不允许删除和编辑”及既有系统账号保护冲突；在没有进一步确认前采用安全口径：权限范围为全部，但角色和内置账号仍不可编辑、停用或删除。
- SQLite、`localStore` 和角色对象中的权限键、角色继承及安全校验是角色授权的唯一真相。角色弹窗保存时必须明确提交用户选择的直接权限，不得误清空未改动的历史授权数据；父角色继承、权限层级展开和禁用状态必须与登录授权计算保持一致。

## 已确认的正式 Mock 人脸口径

- 正式 Mock 环境的人脸识别使用已经部署的服务端人脸服务，不要求启动或补建本机 `faceai-server`。
- 后续审计不得把未运行本机人脸服务判定为客户端缺失，也不得修改正式 Mock 或只读 Mock 资产来伪造客户端闭环。

## 已确认的 Android 实机人脸口径

- 用户于 2026-08-06 提供的多脸指南覆盖 2026-08-04 的旧单图上传口径。员工人脸为 1:N，所有图片平等；服务端 `faceId` 与原生 `faceAiId=${employeeId}_${faceId}` 必须分开保存。
- 实机录入先用临时原生 ID 采集，再通过通用 `http.multipart` 调用 `POST /api/v1/employee/face/image`（`employeeId + file`）并校验 SHA-256，随后调用 `POST /api/v1/employee/face`（`employeeId + faceFeature + faceImagePath + fileHash`）。服务端明确返回业务成功和 `faceId` 后才能替换为最终 FaceAISDK 模板并保存 SQLite。
- 后台建档、最终模板或 SQLite 任一步失败都不得显示“本机已录入”，不得提供旧 `/api/v1/face/upload` 重试；两步写请求不在启动、联网恢复、定时任务或 outbox 中自动重放。若后台已建档但本机收尾失败，只通过后续增量同步恢复。
- 图片 SHA-256 全局去重。每人上限由服务端配置并返回失败，客户端不硬编码默认 3，也不把 `system.face.maxPerEmployee` 加入设备配置。
- 服务器同步严格处理 `ADD/status=0` 与 `DELETE/status=9`，按 `faceAiId` 导入或移除 FaceAISDK；MQTT `faceChanged` 立即触发增量拉取，另每 5 分钟执行 HTTP 增量拉取。

## 已确认的员工指纹范围

- 客户于 2026-07-30 最新确认：当前版本暂时放弃员工指纹功能，默认配置不得开启指纹。
- 首页取卡方式、管理员页面、系统页面、人员页面和设备设置中不得显示员工指纹入口、状态、阈值或开关；指纹页面不得注册为可访问路由。
- 后端指纹字段、同步契约、SQLite 兼容字段和暂未接线的底层能力可以保留，避免破坏数据兼容；这些保留项不属于用户可见功能，也不得再计入未完成项或完成度分母。
- 用户于 2026-08-08 明确 SQLite 不为指纹单独建表：唯一物理生物绑定表仍命名为 `face_bindings`，使用 `biometric_type=FACE/FINGER` 区分记录，人脸照片字段也保存在 FACE 行；旧 `face_bindings`、`face_photos`、`finger_bindings` 事务迁移完成后只保留新 `face_bindings`，不得新增 `biometric_records`。人脸和指纹原始特征都不落库。
- 设备自检不得因为保留的指纹配置或底层能力缺失而判定失败。只有客户后续明确恢复员工指纹范围时，才能重新开放入口和实现闭环。
