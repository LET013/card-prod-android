## 人脸识别关闭后 FaceDetectorV2Jni 持续运行修复

**问题**: 人脸识别 UI 关闭后，日志中 `FaceDetectorV2Jni.detectFacesImageByteBuffer` 持续滚动，说明 CameraX 帧分析器和 FaceSearchEngine 未被停止。

**根因**: `JsBridgeV2.java` 中 `createFaceCallback()` 的两个回调直接丢弃了 `currentFaceController` 引用：
1. `onCancelled()` - 直接 `currentFaceController = null`，未调 `controller.stop()`
2. `onFaceEnrolled()` - 同上

对比正确路径 `cancelCurrentFaceOperation()` 是先调 `controller.stop()`（内部会 `clearFaceAnalyzer()` + `FaceSearchEngine.stopSearchProcess()`），再置 null。

**修复**:
- `onCancelled()` 和 `onFaceEnrolled()` 中，在置 null 前先调用 `controller.stop()` 清理 CameraX Analyzer 和 FaceSearchEngine
- `onFaceVerified()` 无需修改，已正确调用 `cancelCurrentFaceOperation()`

## 人脸识别成功后"卡柜01出卡失败"修复

**问题**: 人脸识别成功后，卡槽样式闪烁后提示"开柜01出卡失败，请稍后重试或联系管理员"。

**错误路径分析**: 用户指出在 `old/DeviceApplicationFacade.java:125` 打断点未触发。确认 V2 架构不经过 old Facade，真实路径是：
`JsBridgeV2.onFaceVerified → emit face.recognized → Vue index.vue → services.takeCard() → takeCardWorkflow.take() → canDispatch → sendSerial`

**根因**: `services/index.js` 中 `canDispatch` 函数只允许 `simulator === true` 的设备发送取卡指令。真实设备（`SERIAL_SIMULATOR_ENABLED = false`）的 `simulator = false`，直接被 `SERIAL_TOPOLOGY_UNCONFIRMED` 拦截，无法发送取卡指令。

**修复**: 修改 `canDispatch` 为真实设备添加路径：
- 统一先检查串口 state === 'CONNECTED'
- 模拟器：`{simulator:true, requiresBoardAck:false}`（不变）
- 真实设备：`{simulator:false, requiresBoardAck:false}`（新增）
- `requiresBoardAck: false` 因为 `DeviceCoreService.onDataReceived` 被注释，ACK 事件到不了 Vue
- 物理确认通过 `slot.status` 事件（onSlotStatus → EventBus 通路正常）

## remoteOpen doorCode 始终为 1 导致 waitForDoorOpenEvent 假阳性修复

**问题**: MQTT remoteOpen 返回 `{code:0, msg:"success"}` 但物理门未打开。用户试用非管理员开门也不成功。

**根因定位**: 解码日志中两次卡槽1轮询帧：
- 开门前 `DDCC0019F00101010101...` → data[1]=0x01, door=1
- 开门后 `DDCC0019F00101030101...` → data[1]=0x01, door=1（work 从 1→3 但 door 不变）

`waitForDoorOpenEvent` 中 `Number(slot?.doorCode) === 1` 在开门前后始终为 true。开门帧 `DDCC0008F001515AA55AA501BB1D` 发出后 ~1.4s，下一次轮询事件就到了，`doorCode=1` 立刻触发 resolve，MQTT 响应在 1.9s 发出（不是预期 5s+ 超时）。

**修复**（`uniapp/src/services/index.js`）:
1. 导入 `parseTakeOpenAck` 从 `takeCardWorkflow.js`（此前只导入 `createTakeCardWorkflow`）
2. `waitForDoorOpenEvent` 新增 `previousDoorCode` 参数:
   - 板级 0x51 应答监听：`serial.dataReceived` + `parseTakeOpenAck` 作为主确认路径（与取卡流程一致）
   - 门状态变化监听：仅当 `previousDoor !== 1` 时允许 `doorCode === 1` 触发（阻止开门前 doorCode 已为 1 的假阳性）
3. `executeAdminOpenDoor` 中记录 `initialSlot?.doorCode` 作为 `previousDoorCode` 传入

**行为变化**:
- doorCode 已为 1 的板子：仅 0x51 板级应答能确认，否则 5s+ 超时返回 `DOOR_STATE_NOT_OPEN` 错误（不再假阳性 success）
- doorCode 不为 1 的板子：轮询确认和板级应答双保险，先到先确认
- 快照读取失败的板子：previousDoorCode=undefined → 退回到原行为（doorCode=1 即触发）

**验证**: `node --check` 通过，`npm run build:h5` 通过。未真机验证。

## RS-485 半双工总线碰撞修复

**问题**: 取卡/开门命令偶发失败，串口日志显示开门命令发出后板子无 0x51 应答，且相邻卡槽的轮询应答也消失了。

**根因**: `DeviceSerialManager.runSendWorker` 中 `serialConn.write()` 后无帧间保护间隙。RS-485 半双工下，手动命令（如开门帧）发出后收发器立即可被下一个轮询帧驱动，若板子此时仍在发上行应答→总线碰撞→双方数据均损坏。

**修复**: `runSendWorker` 每次 `write()` 后插入 30ms `Thread.sleep()`，让 RS-485 收发器有足够时间从"发"翻转到"收"方向。对 10 槽设备每轮仅增加 300ms，总体影响忽略不计。

**验证**: 真机验证正常。

## 取卡选举优先级修正

**问题**: 人脸识别后提示"当前暂无可用工作卡，请联系管理员"。

**根因分析**: `takeCardElection.js` 中 `CONDITION_PRIORITY` 将 FULL(0) 和 OCCUPIED(1) 分成两级，用户要求"充满了或不在充电"应同优先：

**正确逻辑**:
1. 优先选 FULL 或 OCCUPIED（充满/不在充电），且有卡在槽的
2. 若所有有卡槽都在 CHARGING 中，则选电池最高的

**修复**: `CONDITION_PRIORITY` 改为 FULL=0, OCCUPIED=0, CHARGING=1。`compareAvailableCharge` 作为同条件内排序（batteryPercent 降序 → voltage 降序 → slotNumber 升序）。

**代码审查结论**: 当前代码已正确将 `cardNo` 作为卡槽属性（`cardNoOf(slot)`），不用作槽位查找键。`cardNo` 仅在选举后从选中槽位提取用于操作记录和事件上报。

## faceCameraMirror 配置不生效修复（2026-08-08 第三次修复 — 根因级）

**问题**: 修改 `faceCameraMirror` 后摄像头预览始终左右镜像，重建 APK 重装也无效。`setScaleX`（包括 wrapper 方案和强制 PERFORMANCE 模式）在 RK3568 上完全不起作用。

**真正根因**: 
1. `PreviewView` 在 RK3568 平台底层使用了 `SurfaceView` 实现。`SurfaceView` 有自己独立的硬件窗口层（hole punching），所有 View 层级的 `setScaleX` 变换（无论作用在 PreviewView 还是父容器 wrapper 上）都不会影响其渲染。
2. `setImplementationMode(PERFORMANCE)` 只是一个提示，PreviewView 在特定设备上可以无声回退到 COMPATIBLE (SurfaceView) 模式。
3. 搜索模式下 `FaceSearchEngine.runSearchWithImageProxy(ImageProxy, rotation)` 不接受 mirror 参数，`cameraMirror` 从未传入 FaceAISDK 搜索路径。

**第三次修复（TextureView 方案）**:
- `activity_main.xml`: 移除 `PreviewView` + `FrameLayout wrapper`，替换为原生 `<TextureView android:id="@+id/camera_preview">`。TextureView 作为普通视图参与 View 层级绘制，不受 SurfaceView 孔窗限制。
- `MainActivity.java`:
  - `mCameraPreviewView` 类型从 `PreviewView` 改为 `TextureView`
  - 移除 `mCameraPreviewWrapper` 和 `setImplementationMode(PERFORMANCE)`
  - 新增 `mSurfaceTextureListener`: 在 `onSurfaceTextureAvailable` 时创建 `Surface` 并 fulfill 待处理的 `SurfaceRequest`；在 `onSurfaceTextureSizeChanged` 时重新应用 mirror
  - 新增 `createPreviewSurfaceProvider()`: 创建 `Surface` 从 TextureView 的 `SurfaceTexture`，提供给 CameraX Preview
  - `applyFacePreviewMirror()`: 改用 `Matrix.setScale(-1/1, 1, pivotX, 0)` + `TextureView.setTransform(matrix)`——通过 OpenGL 纹理级变换实现镜像，完全不依赖 View 层级 scaleX
- `FaceEnrollmentController.java`: 新增诊断日志（`setCameraConfig`/`processEnrollFrame`/`processSearchFrame`），标记搜索模式 `cameraMirror` 仅影响预览不影响搜索输入（因为 `runSearchWithImageProxy` 不接受 mirror 参数）

**关键差异**:
| 方案 | 底层机制 | RK3568 有效？ |
|------|---------|:---:|
| setScaleX on View/Wrapper | View 层级变换，SurfaceView 孔窗绕过 | ❌ |
| setImplementationMode(PERFORMANCE) | 提示用 TextureView，设备可能忽略 | ❌ |
| TextureView.setTransform(Matrix) | OpenGL 纹理矩阵，与 SurfaceView 无关 | ✅ |

**验证**: Java 编译 BUILD SUCCESSFUL，JS 语法检查 + H5 构建通过。真机未验证。

## "该员工已有未终结的取卡操作"误拦截修复

**问题**: 人脸识别后提示"该员工已有未终结的取卡操作，暂不能重复执行"。

**根因**: `takeCardWorkflow.js:434-444` 中每次取卡前查询 `listRecoverableOperations`，若发现同一员工有任何状态为 `RECEIVED/SELECTING/VALIDATED/QUEUED/SERIAL_SENT/BOARD_ACKED/PHYSICAL_PENDING` 的历史取卡操作，就抛错阻止。一旦某次操作因 crash/杀进程卡在中间状态（如 RECEIVED），该员工后续全部取卡被永久拦截。

**修复**: 删除该段拦截代码及 `ACTIVE_TAKE_STATES` 常量。依据：2026-08-08 用户已明确"不存在员工持有未归还工卡这一客户端业务状态，不得根据历史 TAKE_CARD / RETURN_CARD 记录阻止员工再次取卡"。`operationId` 每次含时间戳+随机串，天然唯一，无需跨操作去重。

**验证**: JS 语法检查通过，24/24 测试通过，H5 构建通过。真机未验证。
