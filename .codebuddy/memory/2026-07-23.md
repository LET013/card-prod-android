## serialport 独立组件串口读取失败修复
- **根因**: 迁移到独立组件时，`open()` 函数用 `memset(&tio, 0)` 清零 termios 结构体，并设置 `VMIN=0, VTIME=0`，导致 `read()` 进入非阻塞轮询模式（始终返回 0 字节）。原始 app 模块使用 `cfmakeraw()` 自动设置 `VMIN=1, VTIME=0`（阻塞等待至少 1 字节）。
- **修复**: 将 `open()` 改写为与原始 app 模块一致的逻辑 — `tcgetattr` 获取当前配置 + `cfmakeraw` 设为原始模式 + 按位修改 `c_cflag`（`CS8 | CREAD | CLOCAL`）+ 清除 `O_NONBLOCK`。同时修复 use-after-free（`ReleaseStringUTFChars` 在日志前调用）、头文件 `closeNative`→`close`/`tcflush` 声明。
- **关键改动**:
  - `VMIN=0` → `cfmakeraw()` 自动设 `VMIN=1`
  - `memset` 清零 → `tcgetattr` 保留驱动配置
  - `c_cflag = flags | CREAD | CLOCAL` → 按位 `&= ~CSIZE; |= CS8 | CREAD | CLOCAL`

## 串口"只有sark运行才能读数据"根因分析 & 修复
- **问题**: 自己 app 的串口在正常情况下读不到数据，只有运行工作卡柜 app (sark) 后才能读到

## 串口通信验证通过 & 锁竞争修复 (2026-07-23)

### 验证结论
- **串口收发完全正常**: 调试 app 和主 app 都能在 57600 bps 下正确收发，响应延迟 7-100ms
- sark app 没有任何 GPIO/sysfs 硬件初始化操作（strace 确认），只是普通 `openat + read/write`
- 硬件是被动应答模式，不会主动推送数据

### 锁竞争根因
- `SerialConnectionManager.writeRaw()` 是 `synchronized` 方法，内部调用 `notifyData()` → JS Bridge 回调，WebView 桥是同步阻塞的
- `pollNext()` 也是 `synchronized`，持锁调用 `writeRaw()`，导致 JS 回调在锁内执行
- 读线程收到数据后需要进入 `synchronized (this)` 块的 `handleReceived()`，被阻塞长达 948ms
- 日志: `Long monitor contention with owner JavaBridge (5429) at SerialConnectionManager.writeRaw(line:293) in handleReceived() for 948ms`

### 修复 (SerialConnectionManager.java)
1. `writeRaw()`: 移除方法级 `synchronized`，仅对 `sentBytes` 自增和 JSON 构造加锁；`notifyData()` 回调移到锁外
2. `pollNext()`: 缩小 `synchronized` 块范围，只覆盖状态检查和 mutation；`writeRaw()` 调用和超时 `notifySlot()` 移到锁外；失败时回退 `pendingAddress`

## 设备启动流程实现 (2026-07-23)

  - `DeviceInfoUtil.java` — 设备信息工具（machineId 获取 / deviceBody 构造）

### 启动流程
1. **Phase 0a**: 版本检查 `GET /api/v1/app-version/check`（失败不阻塞，forceUpdate+versionCode>current 时发 FORCE_UPDATE 事件）
2. **Phase 0b**: 设备注册 `POST /api/v1/device/register`（Anonymous）→ 获取 deviceToken + deviceCode
3. **Phase A**: 设备激活 `POST /api/v1/device/activate`（Bearer deviceToken）
   - Path A: `valid=true` → 直接获得 mqttPassword/signingKey/clientId → 跳到 Phase C
   - Path B: 返回 `registerCode` → 发 WAITING_ACTIVATION_CODE 事件 → CountDownLatch 等待 5 分钟
4. **Phase B**: Activity 输入激活码 → EventBus post `BootstrapActionEvent(PROVIDE_ACTIVATION_CODE)` → `POST /api/v1/device/verify` → 获得凭证
5. **Phase C**: 获取配置 `GET /api/v1/device/config` → communicationMode (MQTT/HTTP)
6. **Phase D**: 
   - MQTT 模式：连接 broker → subscribe `card/{deviceCode}/down` + `/down/response` → 发 login 报文（HMAC 签名） → 等待 loginResp (code=0, 15s 超时)
   - HTTP 模式：`POST /api/v1/device/login`
7. **完成后**: 启动 HeartbeatManager（60s 间隔，MQTT topic `card/{deviceCode}/heartbeat` QoS 0）
   - 发 EventBus `BootstrapEvent(Phase.RUNNING)`

### Activity 集成要点
- Activity 注册 `@Subscribe` 监听 `BootstrapEvent`，根据 `Phase` 显示进度或激活码输入框
- Activity 输入激活码后 post `BootstrapActionEvent(PROVIDE_ACTIVATION_CODE, code)`
- 启动 Service: `startService(intent)` 传入 `EXTRA_SERVER_URL`, `EXTRA_MQTT_HOST`, `EXTRA_MQTT_PORT`
