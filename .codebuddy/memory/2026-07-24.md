## 串口轮询方案重设计文档（2026-07-24）

分析了当前 `SerialConnectionManager.pollNext()` 的 5 个问题（轮询线程做同步 I/O、与手动命令互斥、单槽位响应匹配、超时依赖周期、无法区分响应类型），并编写了完整重设计方案 `docs/SERIAL_POLLING_REDESIGN.md`。

核心方案：**SendQueue（ArrayBlockingQueue）+ SendWorker Thread（串行发送 + CountDownLatch 等待响应）+ Polling Scheduler（独立 ScheduledExecutor，只加队列不做 I/O）**

设计涵盖：
- SendTask 任务结构（带 latch 的手动命令 vs 发后不管的轮询）
- SendWorker 主循环（queue.poll → serialManager.send → latch.await 等待响应或超时）
- Polling Scheduler（每 350ms 往队列 offer 轮询任务，满则丢弃）
- 手动命令改造（openDoor/querySlot/readVersion 统一走 sendAndWait）
- handleFrame 响应匹配（地址 + 功能码双重校验，释放 latch）
- 并发安全分析（AtomicReference + BlockingQueue + 独立 CountDownLatch）
- 与旧方案 9 项对比
- 测试建议（4 项单元 + 6 项集成）

## 串口轮询方案第二轮更新（2026-07-24）

### 双队列优先级 + 批量轮询去重
- 手动命令 `put` 入 manualQueue(32)，轮询 `offer` 入 pollQueue(256)
- SendWorker 每次循环 `manualQueue.poll()` 非阻塞检查，为空时才 `pollQueue.poll(1s)`
- enqueuePollBatch 遍历 [start, end] 一次性加入全部槽位；`pendingPollSlots[addr]` 去重，每槽位最多一个待处理任务

### 架构重构：四层分离 + SerialConnectionManager 纯化
用户要求 SerialConnectionManager 变得更纯粹，只做串口收发管理。最终分工：

1. **SerialConnectionManager (纯 I/O, ~180行)**: 只知 byte[]，不知 Frame/Address/Slot
   - open/close/reconnect/isOpen
   - write(byte[]) — 线程安全阻塞写入（内部 LinkedBlockingQueue + WriteWorker）
   - setOnDataReceived(Consumer<byte[]>)
   - snapshot()/getSentBytes/getReceivedBytes
   
2. **DeviceSerialManager (协议调度)**: 持有双队列 + SendWorker + Polling Scheduler + pendingPollSlots
   - openDoor/querySlot/readVersion → 构造 WorkCardProtocol 帧 → put manualQueue → latch.await
   - enqueuePollBatch → offer pollQueue + 去重
   - currentTask (AtomicReference) → 响应匹配
   
3. **SerialMessageRouter (帧路由)**: decode bytes → route(Frame) → SlotStateManager / onResponseMatched

4. **SlotStateManager (状态缓存+订阅)**: Map<addr,SlotState> + subscribeAll/subscribeSlots + 1s检查 + 60s兜底全量推送

DeviceCoreService 变更：`new DeviceSerialManager()` 替代 `new SerialConnectionManager()`，SerialPort 委托目标换一个对象。

文档完整性校验：SerialConnectionManager 对 10 项协议概念不知情（WorkCardProtocol/slaveAddress/function code/slot/polling/openDoor/SendTask/CountDownLatch/pendingPollSlots/SlotStateManager），仅知 byte[] + SerialManager(JNI) + port/baudRate + stats。

## JsBridge 重新设计分析 V2（2026-07-24）

V1 已重写为 V2。核心变更：从"业务路由层"变为"纯能力通道层"，全部业务逻辑归还 Vue。

五大能力通道（零业务逻辑）：
1. **启动流程** — Vue 调一次 `bootstrap.start`，Java 托管全部流程（注册→激活→登录→心跳），进度/激活码/成功/失败通过事件回传
2. **HTTP 通道** — 只暴露 `get(path)` / `post(path, body)` 原始方法，不映射业务 ApiService
3. **MQTT 通道** — `send(cmd, data)` + `loginStatus()` + `handleMessage(cmd)` 按 cmd 注册监听，未注册的消息不转发 Vue
4. **串口通道** — `send(hex)` 发送 + `getLogs(count)` 读环形缓冲(500条) + `subscribe(cmd)`/`unsubscribe(cmd)` 按功能码订阅帧
5. **持久化存储** — SQLite 原始 SQL 执行: `storage.query(sql, params)` + `storage.execute(sql, params)`，参数化查询防注入
6. **人脸识别** — `face.recognition.start` 发起 1:N 搜索 + `face.enrollment.start` 发起录入，faceId 组合规则由 Vue 决定，结果全部走事件异步推送（recognized/enrolled/timeout/error/cancelled）。依赖 `FaceEnrollmentController`（MainActivity 常驻相机 + face_overlay），需小幅改造移除 old/DeviceRuntimeRegistry 依赖，改为注入 FeatureExtractor + threshold。

## bootstrap.start 30s 超时修复 (2026-07-24)

### 现象
Vue 启动页显示 `Request "bootstrap.start" timed out after 30000ms`

### 根因分析
三处问题叠加导致：

1. **`splash.vue` 在 bootstrap 前调用 `loadSettings()` → `http.get`**：此时 `httpClient` 为 null（bootstrap 未完成），调用必然失败。即使 `executeHttpSync` 快速抛 IOException，整个 `request() → ioExecutor → UI thread → evaluateJavascript` 链路上任一环节延迟都可能导致 `bootstrap.start` 在 ioExecutor 上排队等待。而 `bootstrap.start` 本身也走同一条链路，若 `postToAndroid` 失败则等 30s 超时。

2. **`postToAndroid` 静默失败**：当 `window.android` / `window.chrome?.webview` / `window.nativeBridge` 都不可用时，只打印错误日志但不抛异常。`request()` 中的 Promise 等不到 resolve/reject，只能等 30s 超时计时器。

3. **消息通道不可用**：`WebViewCompat.addWebMessageListener` 创建的 `window.android` 对象注入时机依赖于 WebView 加载完成，可能存在竞态。

### 修复

#### nativeBridge.js
- **`postToAndroid`**: 通道不可用时 `throw Error`（而非静默日志），让 `request()` 立即 reject
- **`request()`**: 捕获 `postToAndroid` 异常，清理 timer/pendingRequests 后立即 reject
- **新增 `isChannelReady()`**: 检查 `window.android.postMessage` 是否可用
- **新增 `waitForChannel(maxWaitMs)`**: 轮询等待通道就绪（100ms 间隔，最多 maxWaitMs）

#### splash.vue
- **`onMounted`**: 900ms 品牌展示后，先调用 `waitForChannel(3000)` 确保通道就绪
- **`startBootstrap()`**: 移除 `loadSettings()` 调用 — 此调用总是失败（httpClient 为 null），直接使用 `DEFAULT_BOOTSTRAP_CONFIG`
- **`navigateToMain()`**: 保留 `loadSettings()` 调用 — 此时 bootstrap 已完成，httpClient 可用

#### services/index.js
- 导出 `waitForChannel`、`isChannelReady`

#### JsBridgeV2.java
- `handleTrustedMessage`: 添加日志 `→ handleTrustedMessage: action=... id=...`
- `sendSuccess`: 添加日志 `← sendSuccess: requestId=... data=...` + 跳过原因
- `sendError`: 添加日志 `← sendError: requestId=... code=... msg=...`
- `handleBootstrapStart`: 添加日志 `bootstrap.start: requestId=... serverUrl=...` + `submitting to ioExecutor...`

重新安装后 logcat 仍显示 `slot.status received but NO listeners registered!`。深入分析发现两个独立问题：

1. **`native.ready` 竞态**：`MainActivity.onPageFinished()` 在 WebView 页面加载完成时发送 `native.ready`，但此时 uni-app 的 JS bundle 可能尚未执行。当 `main.js` 的 `createApp()` 注册 `native.ready` 监听器时，事件已被错过。
2. **JS 侧从未主动调用 `app.ready`**：搜索全部 JS 源码未找到 `app.ready` 调用。`native.ready` 唯一来源是 Android 侧的 `onPageFinished`。

### 修复
在 `main.js` 的 `createApp()` 中，**立即调用** `hydrateProjection()`，不再等待 `native.ready`。同时保留 `native.ready` 监听器作为兜底（处理延迟到达的情况）。

`hydrateProjection()` → `services.loadSettings()` → `httpGet('/device/config')` → `replaceSettingsProjection()` → `initSlotsFromTotal()`。
`httpGet` 依赖 `nativeBridge.init()` 创建的 `window.NativeBridge`，而 `init()` 已在 `createApp()` 中先行调用，因此 HTTP 请求可以正常工作。

### 关于 splash → config → index 导航路径
`navigateToMain()` 中若 `settings.initialized` 为 falsy 会导航到 config 页。但监听器已在 `main.js` 注册，且 `appState.slots` 是 Vue reactive 数组，无论在哪个页面被 `upsertSlotProjection` 更新，导航到 index 后 `displaySlots` computed 都会反映最新状态。
